# 讲章笔记 Prompt Cache A/B｜2026-09-28

## 范围与设计

同一 `gpt-5.6` Responses 请求构造、相同合成讲章输入和 `reasoning.effort=high`，仅比较缓存配置：A 沿用默认隐式缓存，B 设 `prompt_cache_options.mode=explicit` 且不放断点。B 按[OpenAI 官方指南](https://developers.openai.com/api/docs/guides/prompt-caching)不会缓存或读取前缀。调用返回的实际模型均为 `gpt-5.6-sol`。脚本和测试在本目录；逐次 API `usage` 原始收据仅保存在 Git 忽略的本地 `artifacts/`，未保存密钥、提示正文或模型文本。

在三份**不同**输入的冷请求中，B 的输入费估计少 $0.008523，即比 A 低 **20.0%**。在 30 分钟内对第一份输入作精确重放时，A 从先前的缓存写入读取 2,820 token，输入费估计比 B 少 $0.010152。后者也说明“一律关闭缓存”会损失重试或重复请求的收益。

## 决策边界

这次 A/B 证实：对本实验中**不同且未复用**的讲章笔记请求，避免缓存写入能降低输入费用；对短时间内**完全重复**的请求，保留隐式缓存明显更便宜。9 月 20 日的[历史计量报告](../../docs/reports/20260920-production-accounting.json)中，213 次 `gpt-6-astra` 调用读取为 0，支持进一步检查实际重复率，但模型、日期和工作负载不同，不能当作本实验的生产基线。

尚未改正式笔记请求。冷请求的 512 输出上限使响应不完整；完整重放的两臂虽然返回可解析 JSON，本实验没有保存文本，也没有运行讲章笔记的内容质量门禁。正式启用 B 前，需要在真实笔记收据中确认同一前缀在 30 分钟内的复用频率，并完成内容质量验证。Layer 2 的稳定政策只有约千余**字符**，不能据此断言达到 GPT‑6 的 1,024 **token**缓存门槛；字段重排仍需单独测量。
