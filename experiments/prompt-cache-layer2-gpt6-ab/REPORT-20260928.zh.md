# GPT‑6 Layer 2 Prompt Cache A/B 实测（2026‑09‑28）

## 结论

对正式 Layer 2 请求的 GPT‑6 Astra 初译、GPT‑6 Sol 独立复核做了 30 次付费实验请求。将周政策共享字段移到 user JSON 最前面，**跨组缓存读取仍为 0，A/B 输入费用估算相同**。长度匹配样本的完整同请求重放却分别读到 1,046 和 1,216 tokens，证明该环境中的 GPT‑6 缓存读取可用。因此目前不建议仅为 prompt caching 调整正式 runner 的字段顺序；这会改变现有请求指纹并影响本地已存模型结果的复用，却没有测得跨组收益。

## 方法与证据边界

- 从 [`scripts/run_target_language_models.py`](../../scripts/run_target_language_models.py) 运行测试夹具的假 caller，捕获正式 runner 构造的 Chat Completions 请求。模型为 `gpt-6-astra`、`gpt-6-sol`；生产组当前把动态 `translationGroupId`、`sourceUnitIds`、`englishUnits`、`context` 放在共享政策前。
- A 保留当前 JSON 字段顺序；B 仅将 `targetLocale`、`terminology`、`scripture`、`formatting` 前置。每对请求的 user JSON 解析值、system 指令、模型和其他参数相同。各模型两组不同合成英文，再重放 B 第一组，共每轮十次。
- 第一轮用测试夹具短政策；第二轮换入 9 月 27 日冻结的西语周政策，但仍使用合成英文；第三轮将合成英文加长，使请求 token 数贴近当周正式 v2 组。保留 `max_completion_tokens=1024` 控制实验成本。第三轮有 `finish_reason=length`，不能据此评价翻译或复核质量。
- 只保存请求 SHA‑256、响应 ID、`usage`、结束原因与耗时。原始请求、响应、密钥和讲章文本未写入 Git。三轮本地回执在忽略目录 `artifacts/prompt-cache-layer2-gpt6-ab*`，计划哈希分别为 `f164cd33`、`34557832`、`180cb421`（前八位）。

## 生产日志对照

只读汇总 `artifacts/post-live-runs/2026-09-27/resi-f8b5a2c5/pipeline/layer2-formal/{es,ko}-v2/group-*-{astra,sol}.raw.json` 中的 `response.usage`：共 768 条 GPT‑6 响应，其中 634 条有缓存写入，**0 条有缓存读取**。两语言的 Astra 中位输入约 1,033–1,035 tokens，Sol 约 1,223–1,235；因此“输入太短”只能解释部分请求。请求构造中变化内容在共享政策之前，使跨组稳定前缀很短；B 虽把字符级共享 user 前缀从 47 增至 2,265 字符，仍没有实测跨组命中。字符不是 token；共享前缀未达到 [官方 1,024 可见 token 门槛](https://developers.openai.com/api/docs/guides/prompt-caching)是最可能的解释，尚未直接测量该前缀的 token 数。

## 优先建议与测量计划

1. **保留当前正式请求与本地产物复用。** [`_model_call`](../../scripts/run_target_language_models.py) 按完整请求指纹复用已完成结果，并用未完成标记避免意外重复付费；这是当前可确认的节费路径。若仅改 JSON 顺序，旧指纹失效，必须处理旧结果与新版本的关系。实验未修改生产代码。
2. **把缓存读写作为持续观测项。** 未来每次 Layer 2 运行按模型、政策版本、语言、组记录 `prompt_tokens`、`cached_tokens`、`cache_write_tokens`、`completion_tokens` 与请求结果复用情况；分别核算普通输入、写入、读取、输出。按政策版本和组长度汇总，避免把本地零请求复用误算成 API 缓存命中。现有 `.raw.json` 可做历史基线，费用为估算，账单需另行核对。
3. **若要争取跨组缓存，先设计有业务意义且超过门槛的固定前缀，再小规模 A/B。** 例如仅在政策确实需要更完整的稳定指令或术语时，把它们放在变化的组内容前；先静态检查相同前缀，再用同政策的两组请求和完全重放正控测 `usage`。不要为凑 token 加无用文本，也不要改动每组独立复核的合同。未测得收益前，不部署该变更。

该 Layer 2 请求没有对话历史或工具定义；其复用对象是单轮固定指令与政策。默认请求未设置 `prompt_cache_key`、缓存模式或保留参数，当前观察到的是 GPT‑6 的隐式缓存。[官方指南](https://developers.openai.com/api/docs/guides/prompt-caching)对 GPT‑6 只支持 `prompt_cache_options.ttl="30m"`（也为默认值），显式键只用于分隔用户等主体的缓存核算，不是改善路由的必要条件。条目是否仍驻留也会影响跨时段重放。只有稳定前缀先达到门槛后，才值得试显式 breakpoint 与模式以避免写入变化内容；键、模式和 TTL 均不绕过 1,024-token 门槛。

用本目录 [`README.zh.md`](README.zh.md) 的命令分别做 dry-run、测试和付费运行。实验脚本为 [`run.py`](run.py)，A/B 不变性与费用公式检查在 [`test_run.py`](test_run.py)。本次三轮请求均返回 HTTP 成功且有 `usage`；测试为 3 项通过。付费结果是缓存和输入费用证据，**不是正式翻译质量、人工批准、发布或真实周生产 A/B 验收**。
