# 工具与实验脚本迁移：执行清单

状态：执行草案，2026-10-17。逐文件基线与建议归属见 [scripts 清单](scripts-inventory.zh.md) §4.15–4.18；目录边界见[布局提案](repository-layout-proposal.zh.md) §2、§4。清单的数量是 2026-10-15 的快照，实施前以当前 `dev`、现有 PR 和调用者重新核对。本页规定搬迁方法，不批准真实运行、发布、删除历史证据或把实验晋级生产。

布局提案 §7–§8 写于 2026-10-02，当时尚未取得目录迁移的实施指示。用户于 2026-10-17 指示继续完成仓库目录迁移。对逐文件证明不在两条实验线活跃闭包内的独立叶子工具，该指示取代了原提案“所有迁移阶段须等两条实验线结束并再次确认”的全局等待条件；它不代表两条实验线已结束，也不授权移动其冻结闭包。每批先核对两条实验线的当前状态及保存的 manifest/运行身份；凡影响活跃实验入口或依赖闭包、归属依赖实验结论，或无法排除影响的文件，仍按 §7–§8 暂缓并记录阻塞原因。OEX 的正式归属仍待实验结论。

## 范围与去向

| 清单归属 | 目标 | 入批条件 |
|---|---|---|
| OPS | `tools/ops/` | 运维、预检、只读审计及发布辅助入口；业务规则已有包内实现时只留下调用它的工具 |
| DEV | `tools/development/` | CI、仓库检查、开发环境与本地诊断工具 |
| EXP | `experiments/`；稳定且可复用的测量入口用 `tools/benchmarks/` | 记录使用环境、输入和退出条件，不因搬目录改变诊断或模拟标签 |
| OEX | 暂不按本清单搬迁 | Prefect、Temporal、诊断 DAG 与 Agents API 的正式归属等实验结论；依[布局提案 §7](repository-layout-proposal.zh.md#7-两条实验线结束前后的决策)另行决定 |

`STAY` 是明确的路径与策略边界，`DEL` 是待核的删除候选；两者均不是本批待搬文件。若工具源文件参与 waiver、policy、execution identity、`frozen_code()`、`CLOSURE` 或其他路径哈希，先按拥有该身份的合同处理，不能当作普通工具叶子搬迁。进行中的冻结运行保持原实现；新路径需要新身份与相应收据。

## 每批先核对

1. 从清单选相互独立的一组文件，先对照布局提案 §7 的两条实验线与保存的 manifest 排除活跃实验闭包；无法确认时不移动该文件。在当前 `dev` 检查 Git 差异、导入者、直接命令、文档链接、CI 清单、部署和外部调用者。`rg` 搜索文件名及裸模块名，同时检查 `except ImportError` 的裸导入、动态 `spec_from_file_location`、`__file__` 根路径和子进程调用。清单 §5–§6 列出已知调用，不能取代当前搜索。
2. 先做原字节 `git mv`，单独提交；接线、入口门面及测试另作提交。不要在搬迁提交里改模型、预算、发布、审核或恢复语义。同一文件若被并行批次修改，串行处理。
3. 保留已被文档、CI 或调用者使用的 `scripts/foo.py` 命令。门面须从仓库外 CWD 可直接执行，必要时也保留 `python -m scripts.foo`、包导入、裸导入及动态文件加载。需要同一模块对象的旧导入使用明确的 `sys.modules` 别名；仅作 CLI 转发的入口不伪装模块同一性。
4. 新实现按目标目录解析仓库根或资源路径。不能借可编辑安装、当前 CWD 或 `sys.path` 的偶然顺序掩盖错误。正式 `tongxing_production` 不反向导入 `tools/`、`scripts/` 或 `experiments/`；工具需要生产规则时调用包的公开接口或既有宿主适配。
5. 同批更新硬编码路径：`.github/workflows/` 的显式命令与测试清单、`py_compile` 或发现根、部署文件、文档和路径身份映射。先检查新模块名是否已被包目录占用；Git 无文本冲突仍可能有 Python 导入遮蔽。

## 验证与报告

- 用合成输入验证旧、新入口的输出、退出码与副作用边界；从仓库外 CWD 运行，覆盖真实调用形式。纯只读工具验证拒绝路径；可能写入或联网的工具用临时目录、合成服务或 dry run，不以生产服务作迁移测试。
- 对包导入、旧门面、动态加载、资源定位及受影响的测试发现做定向检查。合并新的 `dev` 后重跑受影响检查；必要时再用当前 head 的 CI 验证完整路由。`tools/*.py` 目前在 Tongxing iOS 路由中保守地走原生合约检查，不能擅自把它们一概列为可跳过；调整路由须同时证明共享生产者仍会触发所需合同检查。
- 每次正式或测试运行导出脱敏[运行报告](../test-run-retrospective.zh.md)，报告独立走 docs-only PR。代码/CI、真实生产、发布 HTTP、设备和场地分别记录，不把目录搬迁等同于生产验收。

## 批次顺序和出口

先搬无入边的只读叶子，再搬同一工具族的共享 helper 与调用者；随后处理 CI/仓库入口及有副作用的运维工具。实验脚本按方案归组，稳定 benchmark 与仍在探索的实验分开。发布、删除旧门面及 OEX 归属作为独立后续批次，要求调用者与运行身份证据。批次 PR 写明原路径、目标路径、兼容入口、身份影响及实际测试；不要把多组无关工具堆成一个无法追溯的 PR。

完成本线的判据：清单中 OPS、DEV、EXP 的每项均有已合并目标路径或明确的保留/阻塞决定；已迁入口的命令和导入仍按合同工作；CI 的显式清单和路径路由覆盖新位置；遗留 `scripts/` 文件能解释为兼容门面、`STAY`、待实验决定或另批处理。生产包迁移、实验晋级和真实交付验收各有自己的出口，不由本清单代替。
