## 实测

### E1 出错：新 v2 拆分规则（2026-10-21 19:54Z，`layer1-fp/e1-rules-8s`）

- 输入：v10 的 ASR 与 Spark MFA 对齐（按哈希复用），`maxUnitSeconds=8.0`，无覆盖，裁判 Claude Opus 5.5 high，6 workers。
- 结果：**709/709 通过**，0 高风险，`approved_for_layer2_shadow`；20 句因没有安全切点保持整句（8.7–13.1 s）并作为清单问题交给裁判，裁判对这 20 句的 `timelineCoherent` 全部给 pass，无需操作者接受。
- 对照：同一对齐、旧规则（v10）拒 4/709；v13（规则改到一半）拒 1/709；v20 要把目标放宽到 10.0 s 并写一条人工覆盖才到 709/709。新规则在更紧的 8 秒目标下零人工干预到达同一结果。
- 时间：裁判 387 s（119 次调用，单次中位 18.7 s，合计 2254 s）；v10 为 414 s。这次 119 次调用都没有辅助模型用量，传输层修复没有被触发。
- 出错结论：拆分规则这一项把本素材的裁判拒绝从 4 句降到 0 句，并省掉 v11、v17–v20 那类"调目标、写覆盖、重判"的人工回合。

### E2 时间：共享裁判缓存下的一次规则改动（2026-10-21 20:04Z，`layer1-fp/e2-determiner-comma`）

- 改动：限定词规则只在无标点的停顿处生效（`the whole | sort of`），带逗号的名词短语（`the hook, | nor do we`）恢复为边界。离线预览：13 句的切分变化，分布在 10 个块里，整句长单元 20 → 13。
- 结果：**43 次调用、151 s**，对 E1 的 119 次、387 s；76 批直接从共享缓存回放。省下 64% 的调用和 61% 的墙钟。没省更多的原因是单元 ID 按块内顺序编号：一句多出一个单元，同块后面的句子单元 ID 全部顺延，它们的批次也要重判。稳定单元 ID 是下一个杠杆。
- 出错：709 句里 1 句被判高风险（`chunk-0010-s002`，`real, concrete, | intensified period`），这个切点在 E1 里**完全相同**却是 pass：裁判对边界情况不稳定。规则层补了"逗号系列（修饰语或列表项）不在中间切，除非后面是从句开头词"，E2b 验证。
- 单次调用中位 20.1 s，与 E1 的 18.7 s 同量级；没有辅助模型用量。

| 轮 | 规则改动 | 离线预览改变的句数 | 实际重判批次 | 墙钟 | 裁判结果 |

- 同一句 `chunk-0010-s002` 三种切法裁判给了 pass / fail / fail，第四种（在同位语 `Antichrist,` 后、主句 `in the end` 前）pass，和裁判自己的建议一致。结论：裁判对边界情况不稳定，规则层越保守、裁判越少被问到边界情况。
