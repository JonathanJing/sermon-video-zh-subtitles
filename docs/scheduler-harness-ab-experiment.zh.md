# DeepSeek Harness 与 Terra 调度 A/B 实验提案

日期：2026-09-20。状态：P2 backlog，未实施、未测试。本提案归属 [Dev 统一 Backlog](backlog.zh.md) 的 `DEV-EXP-004`；不改变现有 CUV 翻译、核验和发布门禁。

- **状态：Backlog / 未实施、未测试。** 本条为新增实验，历史 backlog 其他条目不因此变为当前计划。
- **目标：** 测试由 DeepSeek 驱动的 agent harness 承担每周证道生产的状态检查、工具调度、失败分类与恢复，减少 Codex 常驻监管消耗。Codex 仅在需修改代码、复杂排障或升级处理时介入。
- **范围：** 首先测试 CUV 翻译及引用核验调度；保持既有翻译/核验模型、工具、输入、缓存及验收规则不变，单独比较调度层。DeepSeek 的具体模型、服务端点和 harness 实现选型在实验准备阶段确定并冻结。

DGX Spark 部署实验：

- **第一阶段：Spark 运行官方 DeepSeek Harness（`dsh`），调用 DeepSeek 云端 API。** Spark 保存任务状态、运行生产脚本、收集结果及执行断点恢复；DeepSeek 判断调度步骤和异常处理，现有翻译/CUV 核验模型保持不变，Codex 仅处理升级的问题。
- 先在隔离目录验证 Linux ARM64、Node.js 和所需插件依赖，检查 Web UI/SSH 访问、进程重启恢复、工具调用及任务锁。官方文档提供 Node.js/SSH 启动方式，但本项目尚未在 Spark 实测，不能标记为已兼容或已部署。
- 固定 Harness 版本或 commit、插件版本、模型和端点；当前为开发者预览版，升级另行验证。GPU 留给需要本地推理的生产任务，调用云端模型的调度程序不要求本地加载该模型。
- **第二阶段：单独评估 Spark 本地模型作为调度后端。** 验证模型插件/接口适配、量化与内存占用、上下文容量、工具调用准确率和恢复能力；不得将“可运行 Harness”等同于“可运行任意完整 DeepSeek 模型”，也不把蒸馏模型能力视为云端模型能力。
- 第一阶段结果与 Codex 对照；第二阶段结果与第一阶段对照，分别记录费用、延迟、正确阻塞率及人工介入。未达到原验收条件时保留现有调度入口。
- 参考：[DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)、[开发者预览说明](https://www.deepseek.com/harness/)、[DGX Spark 硬件说明](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)。

调度 A/B 对照扩展：Terra（2026-09-20）

- **状态：Backlog / 待测试。** 加入 Codex `gpt-5.6-terra` 作为调度候选，评估降低调度模型成本和额度消耗后，是否仍能保持证据核验与恢复可靠性。
- **A：现有 Codex 调度基线。** 记录实际模型、推理档位、运行环境及版本，不以历史时间窗口总 tokens 代替本次基线。
- **B：Codex Terra 调度。** 使用 `gpt-5.6-terra`，尽可能保持与 A 相同的 harness、工具、提示、权限、上下文装载及任务状态；冻结推理档位并记录不可避免的差异，主要比较调度模型变化。
- **C：Spark 上的 DeepSeek Harness + DeepSeek API。** 与 A/B 使用同一业务任务和工具合同；由于 harness 与模型同时变化，将其标为整套方案对照，不能把差异全部归因于模型。
- A/B/C 使用同一批正常与故障任务、相同初始缓存快照、相同生产翻译/核验模型，独立输出目录，避免后跑组继承前组新增缓存；交错运行并重复测试，记录样本数和波动。Spark 本地模型仍为后续独立候选。
- 验收沿用上述正确阻塞、引用完整性、人工审批及不真实发布的条件；另外比较完成率、误放行/误阻塞、恢复成功率、升级次数、耗时和费用。分别报告每组调度 tokens 与生产 API tokens。
- Terra 仍属于 Codex 调度方案，不预设其节省额度的比例；能获取账户额度变化时单独记录并注明同期其他任务干扰，不能由 tokens 或模型名称直接推算。原 80% 节省目标作为候选方案实验目标，报告实际结果，未达目标亦保留结论。
- 交付 A/B/C 比较表及推荐结论：保留当前方案、切换 Terra、采用 DeepSeek Harness，或按常规调度/复杂异常分层路由。测试结果通过前不切换正式入口。

实验步骤：

1. 冻结相同 source/hash、引用映射、模型响应缓存与初始状态；以本周成功及失败证据构造脱敏离线回放。保留 Codex 调度作为对照。
2. 用明确的状态机与结构化工具结果驱动 harness；长运行交给进程及事件通知，恢复时只载入必要状态，不反复发送完整对话。保持任务锁、幂等、依赖失效、重试上限和断点续跑。
3. 覆盖正常完成、重复经文定位、缺真实图片、证据不确定、缓存失效、模型/API错误、进程中断及重复调度。验证该阻塞时阻塞、该升级时升级；相同失败且无新证据不得反复请求模型。
4. 离线通过后，再做隔离的真实小规模 A/B。预先约定调用预算和停止条件，测试环境禁止真实发布；人工审批、发布授权和证据链规则保持原样。

测量与验收：

- 分开统计 Codex 调度、DeepSeek 调度和生产模型 API 的输入、缓存输入、非缓存输入、输出 tokens、调用次数及可得费用；记录墙钟时间、完成率、人工/Codex 介入次数和错误重试。不能将 token 数直接换算为 Codex 账户额度或跨模型费用。
- 对照使用同一任务集合、相同初始缓存和明确起止边界；历史 Codex 时间窗口统计混有其他操作，不能作为严格 CUV 专属基线。
- 所有关键阻塞用例必须阻止错误交付；不得丢失重复引用、放宽 CUV 精确匹配、伪造人工通过，或在证据缺失时继续翻译/发布。
- **建议实验目标（待实测）：** Codex 调度调用量及非缓存输入+输出 tokens 较对照下降至少 80%；同时报告包括缓存输入的总量与可观测账户额度变化。生产通过率和证据完整性不下降，总费用/耗时的变化必须披露。
- 交付比较报告、可重复执行的测试命令、失败案例与回退步骤；只有数据支持后，另行决定是否替换正式调度入口。
