# Layer 2 插件审核下的组级并行（设计草案）

## 现状

- 策略 `batching.workers` 为 16，控制器允许最多 16 个组并行，同一 job root 下 API 在途上限为 24。
- 但 `scripts/run_target_language_models.py` 在传入语言审核插件（`--plugin`）且不是模拟运行时，强制 `workers = 1`（约第 961–963 行）。
- 原因写在代码注释里：插件拒绝后会写入"停止后续派发"的收据，串行化是为了让这个承诺与实际执行一致。
- 结果：默认 v1/v2 带插件路径整轮串行；已采用 failure_collector 的 v3 正式路径不受此限制。2026-10-10 的 clip 影子运行记录为 `requestedWorkers: 16, workers: 1`。

## 已有的替代路径（已决定采用）

- 第 949–959 行的 `failure_collector` 分支已经允许组并行：插件拒绝只记录，不写停止收据，轮次继续；系统性停止只阻止后续派发，已在途的组正常完成。
- 该分支由 v3 自动修复执行配置（`sermon-canonical-layer2-execution-v3` 的 `layer2AutoRepair.groupWorkers`，上限 16）驱动，即当前 v3 正式路径。因此不需要新建版本，只需让运行使用 v3。
- 本提案不向已有 v1–v3 配置添加新语义。影子模式与新的停止行为必须使用独立版本合同，并保持旧配置的冻结身份。

## 拟议方向

剩余差异是默认 v1/v2 插件路径的并行化与单次拒绝即停止派发；v3 正式路径已有并行收集语义，不需要重复实现。若要为默认路径提供新行为，必须满足：

1. 插件第一次拒绝时，设置独立且线程安全的立即停止派发信号；不复用 `FailureCollector` 的同错误达到至少三次才系统性停止的阈值。已在途组仍完成并记账。v3 原有收集行为保持不变。
2. 系统性失败（例如同一错误连续出现）停止新的派发，在途组完成后再汇总结束。
3. 每组的翻译和审核仍按顺序完成，组之间不共享状态；聚合顺序仍按源顺序。
4. 并行度受策略 `workers` 和执行配置上限约束（当前 16，同一 job root 的 API 在途 24），不超过预算预留的请求数。24 个文件锁不是跨 job root 或账号总上限；跨运行容量须另经已有全局资源准入层协调。
5. 新停止收据必须分配新 schema 版本，记录实际已派发、已完成、在途、未派发的 group ID 集合及失败触发组；不能复用串行 v1 收据按源顺序推定的 `completedBefore`／`notDispatchedAfter`。旧收据只恢复旧串行路径，新配置绑定新收据版本，迁移必须显式重新冻结。
6. 会计记录 `requestedWorkers`、`workers`、`maxInFlightGroups`，并区分派发前拒绝与在途失败。

## 需要的测试

- 插件拒绝一组：其他在途组完成，后续派发被阻止，结果汇总包含失败记录。
- 系统性失败：不再派发，已在途组完成，不产生"成功"收据。
- 独立串行／并行运行比较源顺序、组内容及其他确定性语义字段；分别验证真实请求收据和不同 request ID，不要求包含唯一 generation 身份的整个候选逐字节一致。
- 预算：并行派发前的预留与串行相同，超限在派发前拒绝。
- 回归：不传插件或模拟运行的行为不变；现有 `workers == 1` 串行路径不变。

## 风险

- 停止语义变化：从"立即停"变为"在途完成后停"，可能在失败后多花一批请求的费用。需要限制在途组数并计入预算。
- 生产路径改动：影响正式运行，需要完整测试和审阅，不能在影子测试中顺便启用。
