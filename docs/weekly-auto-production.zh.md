# 周六自动开工：从 Drive 新文件到页面发布

状态：**已在生产机 mbp16 上安装；2026-11-25 做过四次演练（到英文表、付费转写、40 句片段做到三条音轨听审、整篇 470 句做到三条音轨听审并走了一次听审退回后的改句重配）；2026-11-26 用上周已发布的那一页在 Dev 站点演练了发布这一段；2026-11-27 起 Layer 1 默认加入 WhisperX 时间轴（英文表审核前完成），真实周六运行还没有发生过，也还没有人在手机上做过整轨听审**。本页说明装了什么、它自己会做什么、在哪里停下来等人、出问题时怎么处理。路线是[逐句优先](sentence-first-agent-production.zh.md)；每个审核步骤和每条通知的设计见[人工审核页与通知](design/review-gates-and-notifications.zh.md)。

长期授权和决定（2026-11-25 用户给出）记录在 [`config/weekly-sermon-auto.json`](../config/weekly-sermon-auto.json)：来源文件夹自动开工；付费转写每周 50 美元上限；页面上的提交算正式结论；英文表批准不要求逐句审完；配音跟不上视频时先由 Opus 口语化、不够再由 Opus 精简。

## 它做什么

```text
周六 18:00–22:00  Drive 监控发现新文件 → 写一个触发文件
                  ↓ 驱动被触发文件唤起（另外每 5 分钟检查一次）
自动              核对来源 → 下载并算哈希 → 切音频 → 打开「开工确认」并通知
                  → 付费转写（先在周预算账本预留）→ WhisperX 对齐 → 拆句 → 打开「英文表批准」并通知
等人              你在审核页提交两个决定（英文表可以带着改字直接批准）
自动              再次核对哈希 → 写开工记录 → 应用你的改字 → 生成英文来源包和收据
                  → 建三语运行目录 → Opus 写本篇用词约定 → Opus 逐句翻译 → 另一个 Opus 独立审计
                  → 口播稿（估计放不下的句子先由 Opus 口语化）→ 预检
                  → 每种语言依次：配音 → 合轨（去静音、逐句加速）→ 同步闸门 → 打开「整轨听审」并通知
等人              你逐条听审；下一种语言同时在配
                  标了问题的句子：Opus 按你写的改字 → 只重配这些句子所在的批次 → 重新合轨 → 这一条再请你听
自动              三条都批准后写出听审结论文件
                  → 生成页面配置 → 发布预检 → 各语言的页面、文稿、字幕、MP3 → 原视频的声音指纹和每种语言的指纹索引
                  → 取线上现状、做第一份快照并核对 → 打开「发布授权」并通知（到这里只写本机文件，没有部署）
等人              你在发布授权页上看三语标题、经文、要做的两次部署，授权或暂不发布
自动              第 1 次部署（页面与资产）→ 逐文件核对线上 → 第二份快照（release、目录、英文对照、现场对齐）
                  → 第 2 次部署 → 回读线上 → 发布完整性门禁 → 打开「发布后确认」并通知
等人              你在手机上把三种语言各打开看一遍，提交确认
页面上线后（配置里开了海报，现在是开的）：起草主视觉概念 → 生成主视觉 → 合成三语海报 → 打开「海报」并通知
等人              你选一张批准（批准就是上传的指示），或者都不用（重画、换概念、本周不发）
自动              按你的名字记下审看 → 绑定到各语言的 release → 取线上现状、做快照并核对 → 部署一次 → 回读
到此为止          研读手册条目、统计目录、学习内容不在这条自动流程里：按 runbook 10.7 继续
```

配置里的 `automation.through` 决定自动做到哪里：`publish`（现在的默认值，用户 2026-11-26 决定）做到页面发布和发布后确认，`tracks` 做到整轨听审，`layer1` 做到英文表批准为止。驱动在生产目录写下 `next-step.json`，里面是接着往下做所需的路径和冻结的决定；之后的步骤仍由人或代理会话按 [runbook](../experiments/sentence-first-agent/AGENTS.md) 执行。

代码从主检出下的 `artifacts/worktrees/weekly-auto`（一个固定在已部署提交上的 worktree）运行，产物也写在这个 worktree 自己的 `artifacts/` 下：路线的脚本按自己所在的检出找运行目录、渲染锁和证据路径，所以代码和产物必须在同一个检出里。生产记录在 `artifacts/weekly-auto/<生产名>/`，Layer 1 来源目录在 `artifacts/sentence-first-agent/<生产名>-source/`，三种语言的运行目录是 `<生产名>-zh`、`-ko`、`-es`。真实生产名是 `<周六日期>-sermon`。这个 worktree 有自己的 `.venv`（`tools/development/worktree_venv.py` 建的），OpenAI 凭据文件仍在主检出，路径记在 `local.json` 的 `envFile`。

安装、查看和卸载都用同一个命令（在部署 worktree 里，用它自己的 `.venv/bin/python`）：

```bash
.venv/bin/python tools/ops/weekly_auto.py agents install --port 8444
```

```bash
.venv/bin/python tools/ops/weekly_auto.py agents status
```

`agents install` 会读出本机的 tailnet 名称并写进 `local.json` 和审核服务的启动参数；`agents uninstall` 卸载两个 LaunchAgent，不动产物。更新代码：在部署 worktree 里 `git fetch origin dev && git checkout --detach origin/dev`，把 WhisperX runtime 的绝对路径写进 `local.json` 的 `whisperxPython`，再运行一次 `agents install`（它会重启驱动；正在做的阶段从已有产物续跑，已配好的句子不会重配）。

WhisperX runtime 不能装进部署 worktree 的 `.venv`；用独立 Python 3.11：

```bash
uv venv artifacts/whisperx-timeline-ab/runtime --python 3.11
uv pip install --python artifacts/whisperx-timeline-ab/runtime/bin/python whisperx==3.8.6
```

`local.json` 示例增加：

```json
"whisperxPython": "/Users/<user>/.../artifacts/whisperx-timeline-ab/runtime/bin/python"
```

新一期到英文表时，先确认 `raw-whisperx.json` 和 review 页时间都是 WhisperX；`setup.json` 的 `timelineSource` 应是 `default_sibling` 或 `explicit`，不是 `parent_explicit`。

## 它守的规则

- **可续跑。** 每一步的产物已经在就跳过；中途停了，下一次运行接着做。
- **失败不自动重试。** 一步失败后，定时运行不会再碰它；人看过之后用 `run --production <名> --retry` 重试这一步。
- **WhisperX 默认在英文表之前。** `transcription.timelineBackend` 默认 `whisperx`：付费转写后先用 WhisperX 对 timing-pass 的分段文本做强制对齐，再用 `raw-whisperx.json` 建句表；你在英文表页看到并批准的就是这份时间轴（不需要再单独批准一次）。对齐失败或 `local.json` 没有 `whisperxPython` 时这一步失败并通知，不会静默退回 `whisper-1`。回滚：把 `timelineBackend` 设为 `whisper-1`，或对该 run 用 `--allow-parent-timeline`。
- **付费先预留。** 转写前在周预算账本（`artifacts/weekly-auto/budget/openai-<年>-W<周>.json`，按花钱当天所在的 ISO 周，不按证道所属的周）按最坏情况预留；超过上限就不发请求。预留用的单价是估算，不是账单。
- **结果不明就停。** 付费步骤没有明确结果时记为未知，之后所有付费步骤都不再发出，直到用 `reconcile --production <名> --outcome charged|not_charged` 对账。
- **决定要再核对一次。** 审核服务只接受当前版本、带着当前哈希的决定；驱动应用之前再把哈希和文件比一遍，对不上就作废，不产生批准；作废之后驱动按现在的文件把这一步重开成新版本并再通知一次，不会停在那里。开工确认绑定的是来源文件和页面上给出的选项（默认值、标题表里这一周的那一行、讲员列表），不是整个配置文件：2026-11-25 一次部署改了配置里别的设置，把一个已经提交的开工确认判成了作废，之后也没有重开。
- **来源只认授权的文件夹。** 不是那个文件夹、不是视频、或者小于 100 MB 的文件不下载，只发通知。
- **同步只用 Opus 改写。** 合轨时先去句首句尾静音、再逐句加速（不超过 1.15 倍）。仍然落后时，先让 Opus 把落后的句子改成更口语的说法，不够再让 Opus 精简；不调用 DeepSeek。每次改写都要过检查：数字不变、不变长、精简不超过一半。两步之后还跟不上就停下并通知，不把落后的音轨拿给你审。估计放不下的句子在第一次配音之前就先口语化，省一次重配。
- **听审退回的句子自己改、自己重配。** 你在整轨听审页把句子标成「有问题」并提交「要求修改」后：
  1. 你标的句子、问题类型和你写的话，连同这一版音轨的哈希和你这一版的听审记录，存进该语言运行目录的 `repair/issues-r<版本>.json`。
  2. Opus 逐句处理（`opus_tasks.py repair`）：你写了改成什么就照改；只说了哪里不对就只改那一处；问题只在声音上的不改字、只重配；看不懂要求的不猜，原样留着并说明哪里不明白。每句都要有答复，缺了或不合格的再问一次，仍然不行这一步就失败，什么都不写。
  3. 改了字的句子写进 `review.json`（备注以 `review fix` 开头），重建口播稿。
  4. 只重配这些句子所在的批次（一批 8 句，同一批共享声音特征，所以整批重配）；其余句子不动。合轨前先把所有句子还原成配音器写出的原始音频，再重新去静音、逐句加速：这两步是确定性的，没重配的句子出来和上一版一样。
  5. 重新合轨、过同步闸门，再打开这一条的听审（版本号加一）并通知你。新一版的页面在每句上标出「按你的要求改了」「重新配音」或「没看懂要求」，显示你上一版写的话和改之前的译文，「这次改的」筛选只列这些句子。
  6. 改句之后如果这条音轨跟不上视频，流程停下并通知，不会为了同步去改别的句子、重配整条：整条你已经听过。
  7. 新一版只需要听改过的句子就可以批准，前提是上一版你已经按「整轨」或「只听标记」听过；上一版没听完的，仍然要听完有标记的句子或整轨。收据里这一版记为「只听这次改的」，整条音轨的听审方式沿用上一版的，并列出之前每一版的听审记录和重配过的句子。页面声称「只听这次改的」而上一版其实没听完时，驱动把听审方式记为不完整。
- **没有授权就不部署，部署不重试。** 发布授权页列出这一个发布意图要做的两次部署和每次改什么；你在页面上授权之前，驱动只写本机文件。授权绑定第一份快照的封存哈希、各语言的 release 和听审结论文件，之后这些文件变了，授权作废并重新请你授权。每次部署走带保护的发布器：线上现状和取快照时不一样就拒绝。一次部署只做一次：快照里已有一次没有以「已部署」结束的尝试时，驱动停下并通知，由人核对线上版本，`run --retry` 也不会再发。
- **发布完整性门禁不过就停。** 第 2 次部署之后回读线上文件，再对目标站点跑 `sfa_publish_gate.py`（带现场对齐时加 `--require-alignment`）；不过就通知「发布门禁没过」，不打开发布后确认，这一期不记为已发布。
- **海报不挡页面，没有批准不上传。** 海报在页面上线并过了门禁之后才做（合成要读线上的页面）。概念由文字模型根据已发布的文稿起草，主视觉由图像模型画，两者都经 Codex CLI 用 ChatGPT 登录调用，不用 API key。候选做好后停在海报页；你批准其中一张，才会把它的三语海报和公告清单上传（一次部署，只能带本页的海报文件，别的页面的公告原样保留）。「都不用」可以选重画、换概念或本周不发，最多三轮。任何一步做不成只发一条「海报没有做成」，流程继续走到发布后确认。海报不会发到聊天或邮件。这一段由 `automation.poster` 打开：2026-11-26 用户在 Dev 上的上传实跑之后决定打开（「周六打开海报」）。
- **演练不发布。** 演练的听审结论和英文包都不是人工批准，发布驱动会拒绝它们，所以演练做完整轨听审就结束。开工确认里选「不出页面」的也到整轨听审为止；选「只出 Dev 审核」的发到 Dev 站点，同样要授权。
- **内存不够就等。** 配音前先看可用内存，不到 15 GiB 不加载模型，发一条通知，之后每次定时检查再试。这台机器上已有另一条配音在跑时（同一时间只允许一个模型副本）也只是等，不发通知，那一条结束后自己开始。
- **英文表带改字的「要求修改」会自己重出。** 你的改字被应用到你看到的那一版上，旧版留存，新版再推送给你批准。只写备注、没有改字的「要求修改」要有人处理。
- **演练不产生批准。** `start --rehearsal` 走完同样的流程，但文件都标为演练：`humanApproval` 为 false，英文包不能用于翻译，听审结论文件写的是 `rehearsal`，通知和页面都带「演练」。`--limit-units N` 只翻译和配音前 N 句，`--quiet` 不发任何通知。

## 目前的限制

- 只支持整段媒体作为窗口、整期形态、单讲员。开工确认里改了窗口或选了片段，驱动会报「决定没能应用」并停下，由人在生产机上处理。
- 整轨听审里只写了备注、没有标出句子的「要求修改」要有人处理：决定会被记下并通知，之后按 runbook 第 9 步改句、重配、重新打开这一步。
- 七件套里自动做前五件（页面与资产、release、目录、英文对照、现场对齐）。**研读手册条目和统计目录没有接上**：发布授权页和发布后确认页都会写明这两件本轮不交付，发布后按 runbook 10.7 手工补；统计目录补之前，本页的赞踩和收听统计接口返回 400。学习内容（大纲与默想）也不在这条流程里。
- 现场对齐只在「跟视频同步」的音轨上做；独立音轨的页面不带对齐。
- 页面的系列名和经文取自[标题表](series-sermon-titles.zh.md)，页面编号是「系列键的第一个词-英文讲题-主日日期」。标题表里找不到这一篇英文讲题，或者经文的书卷认不出来，流程停在「页面配置」并通知；系列的韩语、西语名称取自同一系列已发布页面的配置，新系列的第一篇要先有人登记。
- 发布前要取一份线上现状：每次发布在生产机上多占约 12 GB（线上现状和两份快照各约 4 GB），可以在发布后确认之后删除。
- 发布后确认之前没有浏览器冒烟；回读和门禁只核对文件。
- 转写提示词只有通用人名加当周英文讲题；两遍转写不一致的句子会在英文表页上标出来。机器不会自己改英文。
- 本篇用词约定由 Opus 根据英文表写出，必须沿用 [`established-terms.json`](../experiments/sentence-first-agent/established-terms.json) 里已发布页面用过的写法；这个文件要在每次发布出现新的固定译名时补一行。约定里和它不一致的写法会被改回已发布的写法，改动记在约定文件的 `correctedToEstablished` 里。
- 讲员的声音文件要先在生产机上：2026-11-25 mbp16 上只有 Eric Geiger 和 John Thomas 的，选其他讲员会被拦下。
- 驱动的阶段记录写在生产目录的 `journal.ndjson` 和 `outcome.json`；各语言运行目录里的脚本仍各自写 `run_status` 的记录，两边没有合并成一个面板。

## 出问题时

| 通知 | 含义 | 做什么 |
|---|---|---|
| 新文件没有开工 | 来源没通过核对 | 确认是不是本周的文件；是的话在生产机上手工开工 |
| 下载失败 | 试了 3 次仍不完整，或 Drive 返回了网页 | 稍后 `run --production <名> --retry` |
| 转写没有开始 · 预算上限 | 本周预留加已用超过上限 | 看账本；确实要做就改配置里的上限（要你决定） |
| 付费请求结果未知 | 转写进程没有干净结束 | 在 OpenAI 用量页核对后 `reconcile`，再 `run --retry` |
| 决定没有生效 | 提交时文件已经变了 | 打开新版本重新审 |
| 决定没能应用 | 驱动做不了页面上选的事 | 看通知里的原因 |
| 失败 · 页面配置 | 标题表里没有这一篇，或经文、系列名补不齐 | 在标题表登记这一周（新系列还要有一份页面配置给出三语系列名），再 `run --retry` |
| 失败 · 第 N 次部署 | 发布器拒绝了（线上现状变了、凭据问题），或上一次尝试结果不明 | 先看生产目录同名的 `-publish` 目录里那份快照的 `deployment-attempt-v2.json` 和线上版本；结果不明时不要重试，按 runbook 第 10 步核对后人工收尾 |
| 海报没有做成 · 页面编号 | 概念草稿、图像生成、合成或上传的某一步失败（常见：Codex CLI 的 ChatGPT 登录过期，要在生产机上重新登录） | 页面不受影响；看通知里的原因，之后按[海报流程](tongxing-weekly-release.zh.md#每周海报交付)手工补 |
| 发布门禁没过 · 页面编号 | 上线后的文件和目录、release 对不上 | 看 `-publish/publish-gate.json` 里失败的检查；这一期不记为已发布，修好后重新过门禁 |
| 配音没有开始 · 内存不够 | 可用内存不到 15 GiB | 关掉占内存的应用；之后会自己再试 |
| 失败 · 某语言同步 | 口语化和精简之后配音仍然跟不上视频；或者按听审意见改句之后跟不上 | 按 runbook 第 7 步人工处理这条音轨，再 `run --retry` |
| 失败 · 改句 | Opus 没有给每个被退回的句子一个可用的答复（已自动再问过一次） | 看该语言运行目录的 `repair/repair-r<版本>-report.json`，确认 Claude CLI 登录有效后 `run --retry` |
| 失败 · 翻译／独立审计／本篇用词约定 | Claude CLI 没有产出合格的文件（已自动重发过一次） | 看生产目录的 `events.ndjson`，确认 Claude CLI 登录有效后 `run --retry` |
