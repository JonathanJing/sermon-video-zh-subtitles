# 周六自动开工：从 Drive 新文件到三条音轨的听审

状态：**已在生产机 mbp16 上安装；2026-11-25 做过三次演练（到英文表、付费转写、40 句片段做到三条音轨听审）；真实的周六运行和整篇长度的运行还没有发生过**。本页说明装了什么、它自己会做什么、在哪里停下来等人、出问题时怎么处理。路线是[逐句优先](sentence-first-agent-production.zh.md)；每个审核步骤和每条通知的设计见[人工审核页与通知](design/review-gates-and-notifications.zh.md)。

长期授权和决定（2026-11-25 用户给出）记录在 [`config/weekly-sermon-auto.json`](../config/weekly-sermon-auto.json)：来源文件夹自动开工；付费转写每周 50 美元上限；页面上的提交算正式结论；英文表批准不要求逐句审完；配音跟不上视频时先由 Opus 口语化、不够再由 Opus 精简。

## 它做什么

```text
周六 18:00–22:00  Drive 监控发现新文件 → 写一个触发文件
                  ↓ 驱动被触发文件唤起（另外每 5 分钟检查一次）
自动              核对来源 → 下载并算哈希 → 切音频 → 打开「开工确认」并通知
                  → 付费转写（先在周预算账本预留）→ 拆句 → 打开「英文表批准」并通知
等人              你在审核页提交两个决定（英文表可以带着改字直接批准）
自动              再次核对哈希 → 写开工记录 → 应用你的改字 → 生成英文来源包和收据
                  → 建三语运行目录 → Opus 写本篇用词约定 → Opus 逐句翻译 → 另一个 Opus 独立审计
                  → 口播稿（估计放不下的句子先由 Opus 口语化）→ 预检
                  → 每种语言依次：配音 → 合轨（去静音、逐句加速）→ 同步闸门 → 打开「整轨听审」并通知
等人              你逐条听审；下一种语言同时在配
                  标了问题的句子：Opus 按你写的改字 → 只重配这些句子所在的批次 → 重新合轨 → 这一条再请你听
自动              三条都批准后写出听审结论文件
到此为止          发布、声音定位、海报还没有自动化：按 runbook 第 10 步继续
```

配置里的 `automation.through` 决定自动做到哪里：`tracks` 做到整轨听审，`layer1` 做到英文表批准为止。驱动在生产目录写下 `next-step.json`，里面是接着往下做所需的路径和冻结的决定；之后的步骤仍由人或代理会话按 [runbook](../experiments/sentence-first-agent/AGENTS.md) 执行。

安装、查看和卸载都用同一个命令（在部署 worktree 里，用它自己的 `.venv/bin/python`）：

```bash
.venv/bin/python tools/ops/weekly_auto.py agents install --port 8444
```

```bash
.venv/bin/python tools/ops/weekly_auto.py agents status
```

`agents install` 会读出本机的 tailnet 名称并写进 `local.json` 和审核服务的启动参数；`agents uninstall` 卸载两个 LaunchAgent，不动产物。更新代码后在部署 worktree 里取到新提交，再运行一次 `agents install`。

## 它守的规则

- **可续跑。** 每一步的产物已经在就跳过；中途停了，下一次运行接着做。
- **失败不自动重试。** 一步失败后，定时运行不会再碰它；人看过之后用 `run --production <名> --retry` 重试这一步。
- **付费先预留。** 转写前在周预算账本（`artifacts/weekly-auto/budget/openai-<年>-W<周>.json`，按花钱当天所在的 ISO 周，不按证道所属的周）按最坏情况预留；超过上限就不发请求。预留用的单价是估算，不是账单。
- **结果不明就停。** 付费步骤没有明确结果时记为未知，之后所有付费步骤都不再发出，直到用 `reconcile --production <名> --outcome charged|not_charged` 对账。
- **决定要再核对一次。** 审核服务只接受当前版本、带着当前哈希的决定；驱动应用之前再把哈希和文件比一遍，对不上就作废，不产生批准。
- **来源只认授权的文件夹。** 不是那个文件夹、不是视频、或者小于 100 MB 的文件不下载，只发通知。
- **同步只用 Opus 改写。** 合轨时先去句首句尾静音、再逐句加速（不超过 1.15 倍）。仍然落后时，先让 Opus 把落后的句子改成更口语的说法，不够再让 Opus 精简；不调用 DeepSeek。每次改写都要过检查：数字不变、不变长、精简不超过一半。两步之后还跟不上就停下并通知，不把落后的音轨拿给你审。估计放不下的句子在第一次配音之前就先口语化，省一次重配。
- **听审退回的句子自己改、自己重配。** 你在整轨听审页把句子标成「有问题」并提交「要求修改」后：
  1. 你标的句子、问题类型和你写的话，连同这一版音轨的哈希和你这一版的听审记录，存进该语言运行目录的 `repair/issues-r<版本>.json`。
  2. Opus 逐句处理（`opus_tasks.py repair`）：你写了改成什么就照改；只说了哪里不对就只改那一处；问题只在声音上的不改字、只重配；看不懂要求的不猜，原样留着并说明哪里不明白。每句都要有答复，缺了或不合格的再问一次，仍然不行这一步就失败，什么都不写。
  3. 改了字的句子写进 `review.json`（备注以 `review fix` 开头），重建口播稿。
  4. 只重配这些句子所在的批次（一批 8 句，同一批共享声音特征，所以整批重配）；其余句子不动。合轨前先把所有句子还原成配音器写出的原始音频，再重新去静音、逐句加速：这两步是确定性的，没重配的句子出来和上一版一样。
  5. 重新合轨、过同步闸门，再打开这一条的听审（版本号加一）并通知你。新一版的页面在每句上标出「按你的要求改了」「重新配音」或「没看懂要求」，显示你上一版写的话和改之前的译文，「这次改的」筛选只列这些句子。
  6. 改句之后如果这条音轨跟不上视频，流程停下并通知，不会为了同步去改别的句子、重配整条：整条你已经听过。
  7. 新一版只需要听改过的句子就可以批准，前提是上一版你已经按「整轨」或「只听标记」听过；上一版没听完的，仍然要听完有标记的句子或整轨。收据里这一版记为「只听这次改的」，整条音轨的听审方式沿用上一版的，并列出之前每一版的听审记录和重配过的句子。页面声称「只听这次改的」而上一版其实没听完时，驱动把听审方式记为不完整。
- **内存不够就等。** 配音前先看可用内存，不到 15 GiB 不加载模型，发一条通知，之后每次定时检查再试。这台机器上已有另一条配音在跑时（同一时间只允许一个模型副本）也只是等，不发通知，那一条结束后自己开始。
- **英文表带改字的「要求修改」会自己重出。** 你的改字被应用到你看到的那一版上，旧版留存，新版再推送给你批准。只写备注、没有改字的「要求修改」要有人处理。
- **演练不产生批准。** `start --rehearsal` 走完同样的流程，但文件都标为演练：`humanApproval` 为 false，英文包不能用于翻译，听审结论文件写的是 `rehearsal`，通知和页面都带「演练」。`--limit-units N` 只翻译和配音前 N 句，`--quiet` 不发任何通知。

## 目前的限制

- 只支持整段媒体作为窗口、整期形态、单讲员。开工确认里改了窗口或选了片段，驱动会报「决定没能应用」并停下，由人在生产机上处理。
- 整轨听审里只写了备注、没有标出句子的「要求修改」要有人处理：决定会被记下并通知，之后按 runbook 第 9 步改句、重配、重新打开这一步。
- 发布、声音定位、研读手册、统计目录、海报、发布后确认都还没有接上；学习内容也没有。
- 转写提示词只有通用人名加当周英文讲题；两遍转写不一致的句子会在英文表页上标出来。机器不会自己改英文。
- 本篇用词约定由 Opus 根据英文表写出，必须沿用 [`established-terms.json`](../experiments/sentence-first-agent/established-terms.json) 里已发布页面用过的写法；这个文件要在每次发布出现新的固定译名时补一行。约定里和它不一致的写法会被改回已发布的写法，改动记在约定文件的 `correctedToEstablished` 里。
- 讲员的声音文件要先在生产机上：2026-11-25 mbp16 上只有 Eric Geiger 和 John Thomas 的，选其他讲员会被拦下。
- 驱动的阶段记录写在生产目录的 `journal.ndjson` 和 `outcome.json`；各语言运行目录里的脚本仍各自写 `run_status` 的记录，两边没有合并成一个面板。

## 出问题时

| 通知 | 含义 | 做什么 |
|---|---|---|
| 新文件没有开工 | 来源没通过核对 | 确认是不是本周的文件；是的话在生产机上手工开工 |
| 下载失败 | 试了 3 次仍不完整，或 Drive 返回了网页 | 稍后 `run --production <名> --retry` |
| 转写没有开始 · 预算上限 | 本周预留加已用超过上限 | 看账本；确实要做就改配置里的上限（要你决定） |
| 付费请求结果未知 | 转写进程没有干净结束 | 在 OpenAI 用量页核对后 `reconcile`，再 `run --retry` |
| 决定没有生效 | 提交时文件已经变了 | 打开新版本重新审 |
| 决定没能应用 | 驱动做不了页面上选的事 | 看通知里的原因 |
| 配音没有开始 · 内存不够 | 可用内存不到 15 GiB | 关掉占内存的应用；之后会自己再试 |
| 失败 · 某语言同步 | 口语化和精简之后配音仍然跟不上视频；或者按听审意见改句之后跟不上 | 按 runbook 第 7 步人工处理这条音轨，再 `run --retry` |
| 失败 · 改句 | Opus 没有给每个被退回的句子一个可用的答复（已自动再问过一次） | 看该语言运行目录的 `repair/repair-r<版本>-report.json`，确认 Claude CLI 登录有效后 `run --retry` |
| 失败 · 翻译／独立审计／本篇用词约定 | Claude CLI 没有产出合格的文件（已自动重发过一次） | 看生产目录的 `events.ndjson`，确认 Claude CLI 登录有效后 `run --retry` |

### 做到整轨听审的演练（`rehearsal-20261125-tracks`）

只取前 40 句，三种语言，不发通知；两个 Layer 1 决定和三个听审决定都由代理直接写入并标明是演练，没有人听过。

| 项目 | 结果 |
|---|---|
| 批准之后到三条音轨可审 | 约 12 分半：用词约定 36 秒，翻译 62 秒，审计 21 秒，口播稿（含配音前的口语化）99 秒，配音 157／144／164 秒，合轨各 15 秒 |
| 翻译 | 每种语言 4 片，全部一次通过检查；审计中文、韩语各提 1 条低级别意见，西语 0 条 |
| 配音前的口语化 | 中文 10 句、韩语 21 句、西语 13 句被采纳 |
| 同步 | 首次合成就过闸门：最大落后中文 1.4 秒、韩语 3.0 秒、西语 3.4 秒；没有触发重配 |

| 整轨听审页 | 从另一台 Mac 经 tailnet 打开：40 句，整轨和逐句音频可播放，视频预览在，非媒体文件拿不到 |

按这个速度估算整篇（约 35 分钟、450 句）：英文表批准之后大约 40 分钟出第一条音轨，之后每条再加 20 多分钟，三条共约一个半小时；如果某种语言要重配，再加 20 多分钟。这是估算，整篇长度还没有跑过。

没有验证的：整篇长度的运行；真实（非演练）运行里带 `--publish` 和已批准英文包的那几步预检；人在手机上做整轨听审；口语化之后仍然落后、需要精简和重配的情况（只在离线测试里走过）。
