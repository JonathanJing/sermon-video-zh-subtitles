## 五、按环节的教训

1. **首次真实运行的链路，先用小样本端到端跑一遍，再上全篇。** 本周文字豁免、试听豁免、v4 发布都是首次真实运行；每个环节的缺陷都在全量数据上才暴露，单次返工 5–15 分钟，累计数小时。
2. **政策阈值要在动工前决定。** 1× 同步门禁上周已拦下全部配音；本周到组装时才讨论，损失 3 小时等待。建议把「尾部滞后预算」「片尾容差」写进本周的 release plan，渲染前读取。
3. **豁免实现哈希与热修复互斥。** 任何对 `IMPLEMENTATION_FILES` 的改动都让已签豁免失效；新能力应放在文件集之外（本次 v3 豁免的做法），或在运行开始前冻结。
4. **Spark 独占会话要覆盖定时任务。** `job-reasoning-review.timer` 两次拉起 27B 推理服务，直接导致三次合成中止和一次豁免链失败。
5. **发布准备必须把网页外壳当整体。** `index.html`、`style.css`、`icons.svg`、worker 与 `.mjs` 必须同版本；构建器应校验引用闭包，而不是固定清单。
6. **线上基线以 Hosting API 为准，不以本地快照为准。** 每次发布前都应取线上版本文件清单核对。

## 九、第一性思考：让发布在没人熬夜守着的情况下完成

把本周的 12.5 小时拆开：计算约 1.5 小时；返工约 5 小时；等人约 5 小时（含 3 小时空闲）。要做到无人值守，必须分别消灭后两项。

**1. 决策前置：把所有人工决定变成发布前填好的一份计划。**
本周 13 次人工介入里，只有 3 次是流程无法预知的（源审核、译文裁决、标题）。其余都可以在周日早上一次性决定：预算、并发、尾部滞后预算、片尾容差、ASR 不一致的处理方式（接受/重合成/文字兜底）、是否做声纹、是否跳 Dev、是否自动合并。建议新增 `release-plan` 的「政策段」，流程只读不问；没有填的项按文档默认值，而不是停下来等。

**2. 停下来等人，只允许三处。**
(a) 源审核；(b) 译文的 `request_human_review`；(c) 发布前的最终放行。其他所有门改为「自动决定 + 记录 + 事后抽查」：文字和音频 QC 的逐句失败按计划里的规则处理（同音字/数字规范化后自动接受；真错读自动重合成一次；再失败则该句字幕兜底），大纲/默想由代理生成后**先发布为待审**（标签「机器生成」），操作者事后批准。

**3. 没有人在的时候，失败要能自愈，而不是等人。**
- 所有 Spark 任务由一个常驻调度器管理：竞争服务出现就等待，内存不足就等待，容器退出非零就按已知错误码自动续跑（本周三次内存中止、三次派发失败都属于可自愈）。
- 每个步骤幂等、可续跑（本周单元缓存、豁免缓存已经做到）；调度器只需反复执行「下一步」直到终态。
- 未知错误才升级给人，并把上下文（日志尾、收据路径、建议动作）推送到手机。

**4. 一次性把链路在小样本上跑通，再上全篇。**
每周正式运行前，先用同一份代码对上周的三分钟片段跑完整链（L1→L4 到 Dev 站），15 分钟内完成；任何缺陷在这里暴露，而不是在 461 句上。本周 80% 的返工都会在这一步被拦住。

**5. 代码与运行分离。**
运行只在冻结的 worktree 和冻结的 Spark 代码目录上进行；运行期间的修复进另一个分支，下周生效。豁免实现哈希不再是运行中的变量。

**6. 发布只有一个入口、一个基线。**
`run_multilingual_cd.py` 读 Hosting API 的线上版本作为基线，构建完整站点快照（含外壳闭包校验），先发 Dev，自动做浏览器冒烟（页面加载、切换本周页面、播放 3 秒），通过后发生产；回滚是同一入口的一条命令。

**7. 让流程自己报告。**
每个环节结束自动导出运行报告并开报告 PR（已有 `export_run_digest.py`），周一早上操作者看到的是一份 INDEX，而不是一个卡住的会话。

按这个设计，周六晚放入源视频后，周日早上应该看到：三语已在 Dev 站可播放；一份计划外的人工决定清单（通常 0–3 项）；一条「放行到生产」的确认。人只在白天做三次决定，其余时间流程自己走。

## 十一、第一性原理：哪里做加法，哪里做减法

### 先问产品到底要防什么

这个产品每周的承诺是：礼拜结束几小时内，听众拿到一份**意思不错**的译文、一条**能听下去且读音对**的配音、一份大纲，并且页面**打得开**、标签**诚实**。按后果排序，真正要防的风险只有六个：

1. 译文把意思译反或漏掉（神学/事实错误）
2. 配音读错关键词（人名、章节、否定、数字）或不可听
3. 页面/目录坏掉，用户打不开
4. 把机器产物冒充人工审核，或讲员/来源归属错误
5. 花钱失控或凭据泄漏
6. 事后无法定位是哪一步出的错，无法修正

合计：本周真正改变产物的门限触发只有 **5 次**（波形核对、ASR 章号、基线过期、标题、静音压缩），而误拦与空转超过 **20 次**，其中最贵的三项（1× 门禁、注错校准、实现哈希）合计吃掉约 4 小时。

### 加法

1. **发布入口的三道新门**：`index.html` 引用闭包校验；部署后浏览器冒烟（打开本周页、切三语、播放 3 秒、字幕出现）；反馈 API 目录同步。这三项对应的恰是本周用户看到的两个故障。
2. **ASR 评分规范化**：按语言把数字书写（삼분의 일 / 3분의 1、二十七亿 / 27亿）、同音字（她/他、忿怒/愤怒、네/내）折叠后再比；章号读法进 TTS 口播规则。预计把 42 句标记降到 6 句以内，其中 5 句是真错。
3. **发布后抽样**：豁免政策承诺的「发布后人工抽样」从未排程。每周一自动出一张 10 句抽听表 + 全部疑点句，操作者 5 分钟内完成，结果写回收据。这比发布前的「人工试听」仪式更诚实，也更便宜。
4. **运行日志的缺口**（见下节）：单一运行时间线、人工等待时长、实际花费。
5. **Spark 独占会话覆盖定时器**，调度器对已知错误自动续跑。
6. **周六小样本全链彩排**，15 分钟内暴露本周 80% 的返工。

### 减法

1. 1× 同步硬门禁 → 计划参数 + 能力标签。
2. 每篇注错校准 → 每月/每次实现变更一次。
3. 实现哈希绑定 → 绑定运行开始时的冻结身份。
4. 逐轮预算仪式 → 周信封。
5. 二级 ASR 全量复核 → 条件触发。
6. Layer 1 时长警告的人工门、Layer 3 源包人工门 → 记录即可。
7. 语言插件里与回译重叠的检查。
8. 收据 schema 蔓延（人工试听 v2/v3/v4、豁免 v1/v2/v3、筛查 v1/v2、内容 v2/v3、目录 v3/v4、发布 v2/v3/v4）：本周为一个 v3 豁免改了 5 个消费者。应收敛为一种收据加 `basis` 字段，消费者只认一种。
9. 版本目录爆炸（文字 QC v1–v15、组装 c1–c5、派发 a1–a6）：工具应原地续跑，失败尝试自动归档，而不是靠人起新名字。
10. Layer 2 独立复核：先量化再定。若下周统计显示复核修复的 12 条里没有意思级错误，则去掉第二模型，把钱留给更便宜的回译抽检。

### log 与账本够不够复盘

**够还原「发生了什么」**：每个产物都有哈希绑定的收据，驱动有 `timings.tsv`，失败尝试（在本会话里是手动）归档后可以按目录对照。本文的时间线就是从文件修改时间重建的。

**不够还原三件事**：

| 缺口 | 现状 | 后果 | 补法 |
|---|---|---|---|
| **为什么**重跑 / 为什么等 | 决定只在聊天里；收据里只有「用户声明」原文 | 复盘要翻聊天记录；云端会话看不到 | 每次人工决定写一条 `decisions.ndjson`（时间、问题、选项、选择、证据路径）；逐句接受记录已经是这个形态，推广到所有门 |
| **等了多久**、等谁 | 没有任何地方记录人工等待；3 小时空闲是从日志空洞推断的 | 无法算出「人」是不是瓶颈 | 驱动在阻塞点写 `waitingOn` 与起止时间；周报自动汇总「计算 / 返工 / 等人」三段 |
| **花了多少钱** | 账本 `source-budget.json` 的 `costMicrousd` 全是 0；真实 usage 只在 27 072 个缓存回复文件里（文字 QC 874 万 token、Layer 2 50 万 token），摘要导出时按规则不复制 | 周报和摘要都看不到成本；预算门的信封其实没人算过 | 账本在每次返回时累计 `usage`，`INDEX.md` 显示 token 与估算费用 |
| Spark 侧日志 | 只有本会话写的派发器会 rsync `render.log`；校准/筛查容器日志靠手动 tail | 内存中止、竞争服务的时间点要靠 journal 反查 | 派发器统一把容器日志、`journalctl` 片段、`nvidia-smi` 快照收进运行目录 |
| 摘要工具 | 2 MB 上限迫使按子目录拆成 11 份；脱敏漏掉内网 IP（11 处手改） | 跨层的因果链被切断 | 上限按文本量而非总量；IP 规则补齐；每周一份总索引 |

结论：账本足以证明「没有偷换规则、没有超预算」，但不足以回答「哪一步慢、谁在等、花了多少、为什么这么决定」。后四个问题才是下周要优化的对象，所以日志加法的优先级高于任何新门限。

## 十二、抛开现有流程：只看任务目的，我会怎么设计

### 前提

这是一个个人项目，页面已经写明「机器质检、未经人工审核」。用户得到的承诺是**快、够用、诚实、错了能改**，不是出版级零错误。本周的证据支持这一点：1383 组译文里第二模型复核零发现，回译 judge 的 64 个标记里真问题 1 个；音频 42 个标记里真读错 6 句。错误率是千分之几，而为了证明它是千分之几，花掉了绝大部分时间。

因此设计的重心应从**发布前证明**挪到**发布后修正**。

### 九条设计

1. **「页」是唯一的产品对象，语言之间彼此独立。** 一页 = 一段原声 + 每种语言各一个不可变版本（文字、音频、大纲）。发布就是把目录指向某个版本；修正就是发一个新版本，只动那一种语言。现在的 v4 发布包已经接近这个模型，但联合发布计划、实现哈希级联、锚点变更作废全部语言这些规则又把它们重新耦合。

2. **一个跑到底的流程器，输入是一份周六填好的计划。** 计划写死本周所有决定：预算信封、标题、尾部滞后、ASR 不一致怎么处理、要不要声纹、发不发 Dev。流程器按步骤跑：接入 → 对齐 → 翻译 → 检查 → 合成 → 组装 → 打包 → 发 Dev → 浏览器冒烟 → 发生产。每一步幂等、内容寻址、失败按错误码自动续跑；只有源审核、译文真疑问、最终放行三处停下等人。本周 13 次人工介入里有 10 次本可以写在计划里。

3. **用「标注 + 抽样」代替「校准 + 豁免」。** 现在的机器质检是一套证明系统：每篇都要用注错样本证明检查器有效，再签一份绑定实现哈希的豁免，消费者逐一验证。本周它证明的东西一次都没变过（检出率始终 99%），却两次让有效豁免作废，一次差点级联到重新合成。换成：每句带上它经过的检查结果（回译分、ASR 一致度、波形核对），页面披露照旧；检查器的校准按模型版本每月离线做一次。发布后每周一抽 10 句加全部疑点句，5 分钟听完，结果回写——这才是真正的人工审核，而且诚实，比发布前让操作者在凌晨声明「人工试听通过」更可信。

4. **修一句话要在 10 分钟内上线。** 本周已知的几处读音和措辞问题，在现在的规则下要走「新修订 → 翻译 → 复核 → QC → 豁免 → 重新合成 → 重新筛查 → 重新发布」，实际会拖到下周甚至不修。应有一个 `fix` 命令：改一句文字或读音，只重合成那一句，重新组装，发该语言的新版本。质量来自修得快，不是来自发前证得严。

5. **预防比检测便宜。** 本周 6 句真读错，5 句是韩语章号读成固有数词，完全可预测。给 TTS 一张口播规则表（人名、章节、数字、经卷名），比事后两级 ASR 加付费复核便宜得多。同理，回译 judge 先按语言折叠同音字和数字写法，再判意思。

6. **配音不追视频。** 产品里字幕跟配音时钟；1× 门禁上周和本周各拦下全部配音一次，带来本周最长的 3 小时等待。配音按自己的时钟发布，与视频的对应关系靠排程表映射；真要同步，那是「同传式精简」这个独立功能的事，单独立项。

7. **Spark 是常驻服务，不是每次 ssh 起容器。** 一个长期运行的 worker 带任务队列，内存和定时器它自己管；Mac 只提交任务、拉结果。本周三次内存中止、多次 hold 丢失对账、竞争服务拦截，都是「每次派发都重新建立独占」这个模式的代价。

8. **发布只有一个入口。** 从 Hosting API 取线上版本当基线，整站快照按 `index.html` 引用闭包生成（本周故障的根因），反馈 API 目录同步是其中一步，先 Dev 后生产，每次部署后无头浏览器打开本周页播 3 秒，回滚是同一命令。

9. **一份运行日志回答四个问题。** 每个阶段写一行：起止时间、结果、等谁、花了多少、为什么重跑。周报从它生成。现在的账本能证明没超预算，却答不出「哪步慢、谁在等、花了多少」，而这三个才是要优化的东西。

### 对现有设计的建议

**保留**
- 四层的数据模型（包、哈希、来源身份）：它让本周的复盘能从文件重建时间线。
- 整轨波形核对、ASR 筛查、基线哈希核对、元数据人工批准、HTTP 逐字节核验：本周 5 次真实抓取全部来自它们。
- 逐句人工接受记录：把人的决定和证据绑在一起的正确形态。

**改**
- ASR 评分做语言规范化；人工试听改成发布后抽样；校准改成按模型版本；哈希绑定改成绑定运行开始时的冻结身份；1× 门禁改成计划参数；二级 ASR 条件触发。

**删**
- 逐轮预算批准文件（本周 82 份）。
- Layer 1 和 Layer 3 两道从未抓到东西的人工门。
- 与回译重叠的语言插件检查。
- 收据 schema 的版本蔓延：一种收据加 `basis` 字段；本周为一个 v3 豁免改了 5 个消费者。
- 先量化再定：第二模型全量复核。它每组花双倍时间和 50 万 token，最终 1383 组全 pass、12 条修复里没见到意思级错误。若下周统计仍如此，把这笔钱换成回译抽检。

### 一个需要操作者做的判断

现在的设计是审计级的，适合「教会官方发布、有责任归属」的场景。如果项目未来会走到那一步，证明体系值得保留，但应放到离线和月度，不放在每周的关键路径上。如果它一直是个人项目，那么复杂度本身已经是最大的故障来源——本周超过 20 次误拦、3 代派发脚本、一次线上回滚，没有一次来自模型，全部来自流程。

### 周日应该是什么样

周六晚放入录像和计划；周日早上看到 Dev 站三语可播、一张 0–3 项的待决清单、一个「放行」按钮；周一 10 分钟抽听，发现问题用 `fix` 当天修。人只在白天做三次决定。

## 十四、再审核：删改清单复核，以及下周的设计与测试计划

### 复核原则

只做两类事：**本周真正让用户或操作者受损的**，以及**改动小、收益确定的**。凡是需要改收据 schema、改多个消费者、或收益要等几周才能验证的，一律推迟。复核后第十一、十二节的清单改动如下。

| 原提案 | 复核结论 | 理由 |

| 删 1× 同步硬门禁 | **改为计划参数，本周做** | 代码已有 `--max-end-lag-seconds` 与 `tailOverrunSeconds`，只差渲染器 CLI 直接吃计划；省掉压缩器的 4 轮往返 |

## 十五、声纹（现场声音定位）怎么改进

### 现状（从代码和本周产物读出）

- 索引：对原声窗口做 8 kHz 频谱地标（`spectral-landmarks-v1`），本周 238 540 个地标、115 685 个 posting、2.59 MB JSON；三语共用一份。客户端采集约 10 s 麦克风音频，本机匹配，给出 `queryStartSeconds`（原声时刻）与置信度。
- 应用：网页 `fieldAlignment.seek(time)` 直接 `audio.currentTime = time`——把**原声时刻当作配音时刻**。
- 本周三语配音在讲道中段落后原声最多 101 s（见 `timing/schedules.json`）。因此即使匹配完全正确，配音也会跳到错的句子。上周之前的页面配音等长于原声，这个 1:1 假设才成立；本周放宽时序门禁后它已不成立。
- 真实麦克风与场地验收连续四周 `not_run`；目前所有准确率数字都来自离线回放。

### 改进（按收益/成本排序）

**1. 先修映射，而不是让配音迁就原声时钟（必须，约 1 天）。**
发布包里已经同时有两套时间：`content` 的 cues 用原声时钟（每组 `start/end`），`captions` 用配音时钟，两者按 `textGroupId` 一一对应。定位结果 `t` 的处理改为：在 cues 里找包含 `t` 的组 → 取该组在 captions 里的起点 → 按组内比例加偏移。网页改 `fieldAlignment.seek`，iOS 改对应的 apply 逻辑；离线测试用 `timing/schedules.json` + `timing/anchor-units.json`：给定原声 500 s，期望落到 zh 第 k 句的配音起点。做完之后，绑定器里「配音必须在原声时钟上」的规则可以整个删掉——它存在的唯一理由就是 1:1 映射。

**2. 做一次真实麦克风测试，再决定其他投入（约 2 小时人工，零开发）。**
笔记本外放 YouTube 原视频，手机在 1 m 和 3 m 处各采集 10 次，用 `fingerprint-diagnostics` 记录匹配分、置信度、端到端延迟；目标 ≥ 90% 命中且误差 < 0.5 s。四周没做这一步，所有后续优化都是在猜。

**3. 从一次性定位改为静默重校（约 0.5 天）。**
配音按自己的时钟走，锁定后会立刻开始相对原声漂移（这是自然语速配音的本性，不是缺陷）。首次锁定后，每 60 s 静默采集 3 s 重新匹配，只在偏差 > 1.5 s 时纠正；麦克风权限只要一次。这样听众听到的始终是「讲员此刻在说的那句」。

**4. 索引提前、瘦身（约 0.25 天）。**
索引只依赖原声窗口，Layer 1 完成就能算（构建脚本已支持 `--precomputed`），不该占发布路径。JSON 转 typed-array 二进制可从 2.6 MB 降到约 1 MB；对场地的手机网络有意义，但先看第 2 项的数据。

**5. 采集时长与阈值。** 10 s 对用户偏长；是否降到 6 s 并允许重试，等第 2 项的真实数据再定。

### 不做

- 不把配音变速去追原声时钟：破坏自然语速，产品已决定字幕跟配音。
- 不做服务端匹配：离线、不上传是这个功能的前提。
- 不按语言分索引：三语共用同一份原声索引是对的。
