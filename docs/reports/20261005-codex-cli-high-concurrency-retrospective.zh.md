# Codex CLI 高并发失败复盘：605.5 秒三语言诊断

2026-10-05 的 r13 使用三语言真实 L2 翻译／独立复核 DAG，配置共享 Codex 业务池 23 槽、每语言 23 个组 worker，Gemini 监督走另一资源池。结论是**当前整条链路在此负载下未通过**；日志没有给出 Codex 账号的固定并发上限，也不能把所有失败归为提供方拒绝推理。[原始阶段报告](20261005-gemini-605s-api-diagnostic.zh.md)和忽略目录 `artifacts/next-concurrency-605s-20261005-r13-gemini/`保留了逐调用证据。

## 实际发生了什么

| 观察 | 证据及含义 |
|---|---|
| 共享池峰值是 23，不是三语言各 23 个实际 CLI 调用 | r13 `profile.json` 设 `businessCodexSlots=23`、`layer2GroupWorkers=23`；共享 broker `resources.json` 的预留区间重算峰值为 23。三个 locale 进程各可建 23 个 worker，即最多 69 个组任务争取同一 23 槽，但 broker 限住了实际 CLI 在途量。 |
| 21 个 CLI 调用记录 WebSocket `403 Forbidden` | zh-Hans 8、ko 4、es 9 个调用的 `events.jsonl` 有到 `chatgpt.com/backend-api/codex/responses` 的重连错误。首批 403 约在 23:46:36 UTC，彼时 broker 仍占满 23 槽。这些调用都有 `turn.completed` 与 usage；CLI 的部分日志明确显示回退 HTTPS 并产出 `agent_message`。403 证明 WebSocket 握手遭拒，**不证明整个模型调用无响应或 23 是官方硬上限**。日志没有提供拒绝的服务端策略原因。 |
| 适配器使这 21 个调用无法成为有效业务结果 | [CLI transport](../../scripts/codex_layer2_transport.py) 对任意 `error` 事件或非消息工具项一律抛 `codex_language_terminal_or_tool_failure_inspect_receipt`，即使 `turn.completed` 且有文本和 usage。21 个调用均没有 `response.json`，资源结果记为 terminal error。这里的严格失败策略避免误收不完整响应，但也将回退后可能完整的结果丢在原始事件中；只能经过身份、内容、schema、来源组和账本核验后考虑恢复，不能直接改成忽略所有错误。 |
| Spark 入场也发生独立故障 | 三语言节点最后均在 `SessionBoundCaller.admit_resource` → `require_session` 的 SSH 响应 JSON 解析处报 `ssh_outcome_unknown_reconcile_before_retry`，约启动后 64–66 秒终止。即使 403 结果能通过适配器，这个错误仍会阻断新调用。空 stdout 的原因未从保留日志查明，不能断言一定由并发造成。21 个未绑定 Spark 任务后来凭本地进程退出完成终态对账；这不等于远端用量已确认。 |
| 调用并非全无产出 | broker 有 90 个 Codex 预留，其中 80 个已释放、10 个在异常时仍 held；59 个调用有 `response.json`。异常和不确定结果没有被自动重发。`turn.completed`/usage 只能证明 CLI 事件中出现了终态及用量，不能代替业务候选准入。 |

此前的[24 路短任务测试](20261005-codex-cli-concurrency-24.zh.md)共 80 次 CLI 调用全部通过，24 路批次 24/24；但使用 8 种短、独立输入的副本，审核读的是旧候选，不是本轮翻译的下游。16 路与 24 路批次分别 31.54 秒、30.15 秒，宽度增加 50% 只缩短墙钟约 4.39%，单任务最长耗时从 22.03 秒增到 30.15 秒。它证明短任务可到 24 路，不能推出三语言长 DAG、共享本地状态和 Spark 守护链路也可稳定跑满 23 路。

## 更安全的并发条件

1. 把 CLI **全局真实在途数**与每 locale worker 数分开：初次重测建议业务池从 4 路开始，依次 8、12、16；三语言可公平分配，例如 8 路按 3/3/2、12 路按 4/4/4。这个数字是保守实验起点，不是账号上限。不要让多个 run 或其他层绕开同一 broker；监督模型若使用 Codex，单独保留 1 槽并计入总在途预算。
2. 每级使用同一冻结输入和完整翻译→审核依赖，覆盖足够长的持续运行，而非只测 24 个短 prompt。记录实际峰值、队列等待、调用 p50/p95、完成组数／分钟、第一次 403、HTTPS 回退数、SSH 未知、候选准入数和已消费额度；扩大宽度必须带来可观察的端到端收益。16→24 的历史短测收益很小，因此 16 以上需要更强证据。
3. 任何新的拒绝、未知结果或远端核验异常都暂停新增派发，保留已完成的邻组和原始回执。先对账，再决定从既有产物恢复；不得把 CLI 未知调用自动重发，也不得在同一身份下偷偷切到付费 API。API 是独立、显式的下一次执行选择。
4. 将连接故障细分为“WebSocket 403 后 HTTPS 完整终态”“CLI 终态失败／无完整响应”“Spark SSH 结果未知”。前者可设计只读收据恢复验证；后两者仍需停止并对账。Spark 入场检查应先在目标并发下稳定返回有身份绑定的 JSON 收据，避免模型池可用而资源门禁失效。
5. 实验通过的条件应同时包含：无未对账任务、每组译文和复核均有有效响应及 schema/来源身份检查、三语候选构建完成、真实墙钟相对低一级有收益。内容质量、人审、后续音频同步和发布另行判定。

因此当前推荐先以 **8–12 路业务 CLI** 做稳定性与恢复验证；若 16 路完整 DAG 的成功率和墙钟都更好，再把 16 升为日常配置。23 路仅保留为待复测的上限实验目标，不能作为已验收的生产宽度。上述建议不会改变 r13 的冻结配置或既有调用收据。
