# 本地模型全部搬到云端 GPU：需要什么资源

日期：2026-10-07。基线：`dev` @ `ba1e237`，10/7 根据 Jony 追问补充并发需求，并按 Codex 审查修正显存、L3 耗时归因、并发假设和方案 B 成本。依据是仓库代码、[GCP 可行性评估](../gcp-production-feasibility-20261001.zh.md)（10/1）、[Spark 8×8 测量](20261003-spark-production-8x8.zh.md)、[10/4 耗时与 token 审计](20261004-production-time-tokens.zh.md)。本次没有开云机器、没有跑模型。**凡标“估”的数字都是推算，不是实测；云厂商价格要在下单前重新核对。**

## 先说结论

1. **每周正式流程里真正跑在本地 GPU 上的只有两个模型**：Qwen3-TTS 1.7B（授权音色 checkpoint，配音）和 Qwen3-ASR 0.6B（配音回转写质检）。英文 ASR 走 `gpt-transcribe` API，`whisper-1` 也是 OpenAI API，翻译和复核走 Sol 6.1 API，它们本来就在云上。Whisper large-v3、Parakeet、Canary 只出现在 live/基准实验里；Spark 上的 27B Q4 `llama-server` 服务的是 live 和实验，不在每周预制主链上。
2. **GPU 不是 12–15 小时的主要来源。** 10/4 真正用到 GPU 的是首轮三语串行配音队列，约 66.78 分钟（474 单元/语言，含装载和校验，不是纯推理；它不在 75.18 分钟的 L3 accounting 区间内）。75.18 分钟那部分是之后的缓存重组和续跑，其中中、韩两次约 21 分钟的重组新合成为 0，91–92% 的时间花在逐句 receipt 全量校验上（见 [音频运行复盘](20261004-runtime-evolution/audio.zh.md)），是 CPU 代码热点，换 GPU 不会变快，要靠复用已验证上下文的代码修复。其余是 L1 英文复核约 48 分钟、L2 各轮 API 约 76 分钟，再加人工批准等待、返工和手动编排。按 10/4 规模，云端 GPU 三语并行估计把约 67 分钟的首轮配音压到约 15–25 分钟，省约 40–50 分钟（估，未分开计时合成、筛查、校验和拼接）；1 小时证道按比例约省 1 小时。不会把 12–15 小时减半。
3. 所以建议：**不要整体迁移**。如果要用云 GPU，只把 L3（TTS + 回转写）做成按需的突发算力，每个语言一张 80GB 卡、批准一个开一个；Spark 继续做默认。并发需求见下面“并发需求”一节。真正想砍墙钟，还是要先解决返工、人工门和手动编排（见项目文件 `analysis/weekly-production-pain-points-2026-10-06.md`，未入库）。

## 每个本地模型需要的资源（按 1 小时证道、三语估算）

工作量假设（估）：按 9/27 的密度（31.5 分钟 → 420 单元），1 小时约 800 单元/语言，三语约 2,400 单元，生成音频合计约 3 小时。

| 模型 / 环节 | 现在在哪跑 | 单份显存（估） | 合适的 GPU | 1 小时证道三语耗时（估） |
|---|---|---|---|---|
| Qwen3-TTS 12Hz 1.7B 授权 checkpoint（正式配音） | Spark CUDA BF16，8 副本 × batch8 | 主权重约 3.4 GB；含 codec、batch8 激活和 CUDA 上下文，估 5–11 GB/副本，**未实测**。Spark 的 GB10 `nvidia-smi` 不给显存数字，8×8 报告里的最低 38.43 GiB 是宿主 `MemAvailable`，不能换算成 GPU 显存 | 8 副本估 40–88 GB 加框架开销：H100/A100 80GB 是候选但不保证够，H200 141GB 有余量；L40S 48GB、L4 24GB 要改代码才能跑 4 或 2 副本（现在只允许 1 或 8） | Spark 实际路径约 1.5–2 小时；H100 约 15–25 分钟；L40S 约 30–45 分钟；单张 L4 约 1.5–2.5 小时 |
| Qwen3-ASR 0.6B（配音回转写质检） | Spark CUDA，canonical 每个 CLI 只装一次 | 约 2–4 GB | 和 TTS 同卡 | H100 约 2–5 分钟；L4 约 5–15 分钟 |
| Qwen3-ForcedAligner 0.6B（legacy 词级对齐） | Spark 优先，MacBook MLX 备用 | 约 2–4 GB | 和 TTS 同卡 | 几分钟 |
| MFA 英文词级对齐 | Spark/Mac CPU | 不用 GPU | 8–16 vCPU、16–32 GB 内存 | 约 5–15 分钟 |
| FFmpeg 解码、拼接、MP3、hash、打包 | CPU | 不用 GPU | 同上 CPU 机器 | 约 5–15 分钟 |
| （可选，不建议）本地文字模型替代 Sol：Qwen3.5 27B / 9B | Spark `llama-server`，仅实验 | 27B BF16 约 54 GB，Q4 约 16–20 GB；9B BF16 约 18 GB | H100 80GB | 未测；9B/27B 的翻译质量没有批准，不能当作 Sol 的等效替换 |

速度推算方法：Spark 8×8 实测 64 句中位 56.81 秒；10/4 实跑每语言 renderer 约 22 分钟/474 单元（含校验和开销）。H100 显存带宽约是 GB10 的 12 倍，但小模型自回归解码还受 kernel 启动和 CPU 开销限制，所以只按 3–5 倍估；L4 带宽和 GB10 接近，单卡只能放 2 副本。这些倍数都没有在本项目的 checkpoint 上测过。

## 并发需求（10/7 补充）

### 实际会同时跑多少

| 层 | 并发来源 | 现有上限（代码事实） | 对云端资源的含义 |
|---|---|---|---|
| L3 单语言 TTS | 一个 renderer 内 8 个驻留副本 × batch8 | 正式 renderer 只接受 `replicas` = 1 或 8（[`render_formal_target_language_speech.py:385`](../../scripts/render_formal_target_language_speech.py)）；16×4 在 Spark 上触发过内存保护 | 一个语言任务就要能放下 8 个副本：显存估 40–88 GB（未实测），主机内存估 64 GB 以上。**80GB 卡只是候选，上限估计会超**；租卡前先测每个副本的 CUDA 峰值（`torch.cuda.max_memory_allocated`）。超过约 70 GB 时，改用 H200 141GB，或改代码允许 4 副本、每语言两张 48GB 卡（新执行身份，需重新验收） |
| L3 回转写 ASR | 每个任务 1 个驻留模型，batch 1–8 | 没有多副本 pool；目前整轨渲染完才开始筛查 | 和同语言 TTS 同卡，额外约 2–4 GB |
| L3 跨语言 | zh / ko / es 各一个渲染任务 | 没有跨任务的 GPU 调度器；两个 8 副本任务放同一张卡会互相抢显存 | **一个语言任务占一张卡**。三语同时跑就是 3 张卡 |
| L2 文字 | 组 worker，API 调用 | 默认每个 run 1 个 active locale；显式 execution-v2 冻结并发配置时最多 3 个（见 [controller 合同](../canonical-layer2-controller.zh.md)） | 走 OpenAI API，不占 GPU。只有改用本地文字模型时才需要 GPU：16 路并发估需 1 张 H100 跑 vLLM，且质量未批准 |
| Sunday live | 现场字幕 | 独立 `live_session`，要求现场设备 | 不在本方案内，继续本地 |

### 三语同时开跑是常态

10/4 三份口语候选分别在 08:57、09:31、09:44 ready，但用的是**同一张批准收据**（10:13，见 [交接与发布复盘](20261004-retrospective/handoffs-and-release.zh.md)）。批准一到，三个语言同时可以渲染；当时只是串行排队，韩、西各多等了 22 和 44 分钟。L2 execution-v2 也允许三语同时生成文字。所以按“批准即派发”，**常态就是 3 个渲染任务同时跑**，要按 3 张卡规划；只有改成逐语言批准时才会错开。L3 超窗回 L2 改译文后的重合成只是局部单元，量小。

### 关键结论：并发几乎不改变成本，只改变“开几张卡”

每周 GPU 总工作量大约固定（估 1–1.5 个 H100 卡时）。三语串行用 1 张卡跑约 1.5 小时，和三张卡各跑约 25–30 分钟，卡时差不多，费用接近；差别在于墙钟和闲置。真正浪费钱的是**为了并发长期开一台多卡机器，等人工批准时也在计费**。

## 推荐方案（按并发修订）

### 方案 A（推荐）：每个语言一张按需大显存卡，批准即开

- 规格：每个语言任务 1 × H100/A100 80GB（先实测显存；不够就 H200 141GB），16 vCPU，64–96 GB 内存，100–200 GB 盘。共同批准时同时 3 张。
- 触发：语言文字批准收据一到就开卡，渲染 + 回转写完就关。
- 平台：Modal / RunPod Serverless（按秒计费，最贴合），或者每任务开一台按需 VM。授权音色 checkpoint 放私有卷，避免每次重新下载。
- 每语言耗时（估）：冷启动和装模型 3–5 分钟，加渲染和筛查约 8–12 分钟（1 小时证道）。三语都批准后，最晚一个语言约 15–20 分钟可听。
- 月成本（估，每月 4 篇）：每周约 1.2–1.8 卡时（含 3 次冷启动），每月 4.8–7.2 卡时。GPU 云按需 H100 约 $2–3.5/卡时：约 $10–25/月；serverless 约 $4–6/卡时：约 $20–45/月；另加约 $5 存储。
- 配额：要确保同一时刻能拿到 3 张 80GB 卡。GCP 上 H100 / A100 的默认配额常为 0，要提前申请；GPU 云要确认区域容量。

### 方案 B：每周开一台 2 卡 80GB 机器

- 2 × H100 / A100 80GB，32 vCPU，192 GB 内存。两种语言并行，第三种排队，最晚一个语言比方案 A 多等一轮（估 15–25 分钟）。
- 简单，只开一台机器；但第二轮只用一张卡，另一张闲着也计费。
- 月成本（估）：每周开约 1–1.5 小时 × 2 卡，每月 8–12 卡时。GPU 云 $2–3.5/卡时约 $16–42/月；按 $2–6/卡时上限约 $16–72/月；GCP H100 约 $10–12/卡时，约 $80–145/月。

### 不推荐：GCP 单张 L4，或 3 卡 / 8 卡常开

单张 L4 放不下 8 副本，跑不了现在的正式 preset。常开多卡机器（例如一台 H100 全月 730 小时）每月 $1,500 以上，完全不划算。

## 仓库里需要改的地方

1. **镜像**：Spark 是 ARM/GB10，云 GPU 基本是 x86。需要一个 linux/amd64 CUDA 镜像，锁定 PyTorch、Qwen TTS/ASR 依赖，不能复制 Spark 的 venv。
2. **派发**：`spark_speech.py`、`run_weekly_dubbing.py` 和 [正式 renderer](../formal-layer3-renderer.zh.md) 的 `--spark-production` 都假设 Spark 主机（SSH/Docker 路径固定）。需要一个云 GPU 后端，或者一个通用的“远端 CUDA worker”适配器。
3. **内存保护和副本数**：8×8 入口用 Linux `MemAvailable < 24 GiB` 当保护，这是针对 Spark 统一内存设计的。独立显卡要改成按 GPU 显存（`torch.cuda.mem_get_info`）保护。如果想用 48GB 或更小的卡，要放开 `replicas ∈ {1, 8}` 的限制（例如允许 4），并当作新的执行身份重新验收。
4. **跨语言并发调度**：现在没有跨任务的 GPU 调度器。云端按“一个语言一张卡”就不需要它，但需要一个小派发器：语言批准收据一到就开卡、跑任务、回传产物和收据、关卡；卡数上限设为 3。L2 controller 的“同 run 一个 active locale”限制不影响 L3，但会限制上游文字批准的节奏。
5. **执行身份**：按 [计算策略](../local-production-compute-policy.zh.md)，换设备/精度就是新的执行身份，云端产物不能和 Spark 产物拼成同一个 render。三语同时在云端跑需要每语言独立任务目录。
6. **策略文档**：现在写的是“Spark 默认、MacBook fallback”。加入云端需要 Jony 决定，并更新这份策略和 `AGENTS.md`。
7. **模型和凭据**：授权音色 checkpoint 只能放私有存储（不能上公开 Hugging Face）；云端的 API key 用平台 secret，不进 Git 和日志。
8. **媒体取得**：项目曾在 Cloud Run 遇到 YouTube bot-check。来源下载继续在本机做、再上传，最省事。
