# 本地模型全部搬到云端 GPU：需要什么资源

日期：2026-10-07。基线：`dev` @ `ba1e237`，10/7 根据 Jony 追问补充并发需求，并按 Codex 审查修正显存、L3 耗时归因、并发假设和方案 B 成本。依据是仓库代码、[GCP 可行性评估](../gcp-production-feasibility-20261001.zh.md)（10/1）、[Spark 8×8 测量](20261003-spark-production-8x8.zh.md)、[10/4 耗时与 token 审计](20261004-production-time-tokens.zh.md)。本次没有开云机器、没有跑模型。**凡标“估”的数字都是推算，不是实测；云厂商价格要在下单前重新核对。**

## 先说结论

1. **每周正式流程里真正跑在本地 GPU 上的只有两个模型**：Qwen3-TTS 1.7B（授权音色 checkpoint，配音）和 Qwen3-ASR 0.6B（配音回转写质检）。英文 ASR 走 `gpt-transcribe` API，`whisper-1` 也是 OpenAI API，翻译和复核走 Sol 6.1 API，它们本来就在云上。Whisper large-v3、Parakeet、Canary 只出现在 live/基准实验里；Spark 上的 27B Q4 `llama-server` 服务的是 live 和实验，不在每周预制主链上。
2. **GPU 不是 12–15 小时的主要来源。** 10/4 真正用到 GPU 的是首轮三语串行配音队列，约 66.78 分钟（474 单元/语言，含装载和校验，不是纯推理；它不在 75.18 分钟的 L3 accounting 区间内）。75.18 分钟那部分是之后的缓存重组和续跑，其中中、韩两次约 21 分钟的重组新合成为 0，91–92% 的时间花在逐句 receipt 全量校验上（见 [音频运行复盘](20261004-runtime-evolution/audio.zh.md)），是 CPU 代码热点，换 GPU 不会变快。之后 renderer 已改为每次运行只建一次 `ValidatedJobContext` 并复用于全部 receipt（`b74071f`），所以这段 10/4 数字是修复前的历史值，修复后的耗时还没有重测。其余是 L1 英文复核约 48 分钟、L2 各轮 API 约 76 分钟，再加人工批准等待、返工和手动编排。按下面统一的计时模型，10/4 规模（474 单元/语言）三语各一张 H100 并行，估计把约 67 分钟的首轮配音压到约 8–12 分钟，省约 55 分钟；1 小时证道（约 800 单元/语言）Spark 串行约 1 小时 50 分，云端约 11–18 分钟，省约 1.5 小时（都是估算，未分开计时合成、筛查、校验和拼接；22 分钟里的 CPU 校验部分换 GPU 不一定变快，所以是偏乐观的上限）。不会把 12–15 小时减半。
3. 所以建议：**不要整体迁移**。如果要用云 GPU，只把 L3（TTS + 回转写）做成按需的突发算力，每个语言一张 80GB 卡、批准一个开一个；Spark 继续做默认。并发需求见下面“并发需求”一节。真正想砍墙钟，还是要先解决返工、人工门和手动编排（见项目文件 `analysis/weekly-production-pain-points-2026-10-06.md`，未入库）。

## 每个本地模型需要的资源（按 1 小时证道、三语估算）

工作量假设（估）：按 9/27 的密度（31.5 分钟 → 420 单元），1 小时约 800 单元/语言，三语约 2,400 单元，生成音频合计约 3 小时。

| 模型 / 环节 | 现在在哪跑 | 单份显存（估） | 合适的 GPU | 1 小时证道三语耗时（估） |
|---|---|---|---|---|
| Qwen3-TTS 12Hz 1.7B 授权 checkpoint（正式配音） | Spark CUDA BF16，8 副本 × batch8 | 主权重约 3.4 GB；含 codec、batch8 激活和 CUDA 上下文，估 5–11 GB/副本，**未实测**。Spark 的 GB10 `nvidia-smi` 不给显存数字，8×8 报告里的最低 38.43 GiB 是宿主 `MemAvailable`，不能换算成 GPU 显存 | 8 副本估 40–88 GB 加框架开销：H100/A100 80GB 是候选但不保证够，H200 141GB 有余量；L40S 48GB、L4 24GB 要改代码才能跑 4 或 2 副本（现在只允许 1 或 8） | Spark 实际路径每语言约 37 分钟，三语串行约 1 小时 50 分；单张 H100 每语言约 8–13 分钟（不含开机）；L40S / L4 需先改副本数，未估 |
| Qwen3-ASR 0.6B（配音回转写质检） | Spark CUDA，canonical 每个 CLI 只装一次 | 约 2–4 GB | 和 TTS 同卡 | H100 约 2–5 分钟；L4 约 5–15 分钟 |
| Qwen3-ForcedAligner 0.6B（legacy 词级对齐） | Spark 优先，MacBook MLX 备用 | 约 2–4 GB | 和 TTS 同卡 | 几分钟 |
| MFA 英文词级对齐 | Spark/Mac CPU | 不用 GPU | 8–16 vCPU、16–32 GB 内存 | 约 5–15 分钟 |
| FFmpeg 解码、拼接、MP3、hash、打包 | CPU | 不用 GPU | 同上 CPU 机器 | 约 5–15 分钟 |
| （可选，不建议）Spark 常驻文字服务 `Qwen3.8-27B-UD-Q4_K_XL-Unsloth` | Spark `llama-server`，live 和实验 | 记录到的进程占用 35,695 MiB（约 34.9 GiB，见 [Spark 独占会话](../spark-exclusive-development-session.zh.md)），含 KV cache；并发加大还会增长 | H100 80GB | 未测；翻译质量没有批准，不能当作 Sol 的等效替换 |
| （可选，不建议）文字实验 `Qwen/Qwen3.5-9B-Base` | 冻结的翻译实验 | BF16 主权重约 18 GB，另加 KV cache | L40S 48GB 或 H100 | 同上 |

**统一计时模型（估）**：Spark 每语言耗时按 10/4 实跑 22.2 分钟/474 单元（约 2.8 秒/单元，含装载、校验和开销）线性外推；单张 H100 每语言 = Spark 耗时 ÷ 3–5，再加开机和装模型 3–5 分钟。所以 474 单元约 8–12 分钟，800 单元约 11–18 分钟。计费窗口再加一次重试余量，按每卡 15–25 分钟算。参考：Spark 8×8 实测 64 句中位 56.81 秒。H100 显存带宽约是 GB10 的 12 倍，但小模型自回归解码还受 kernel 启动和 CPU 开销限制，所以只按 3–5 倍估；L4 带宽和 GB10 接近，单卡只能放 2 副本。这些倍数都没有在本项目的 checkpoint 上测过。

## 并发需求（10/7 补充）

### 实际会同时跑多少

| 层 | 并发来源 | 现有上限（代码事实） | 对云端资源的含义 |
|---|---|---|---|
| L3 单语言 TTS | 一个 renderer 内 8 个驻留副本 × batch8；只适用于**新建的单讲员任务**（`--spark-production`，每个单元都用同一个 adapter speaker，否则 renderer 拒绝 8 副本）。多讲员任务或冻结为旧配置的任务只能用 1 副本，单卡 24–48GB 就够，但会慢很多 | 正式 renderer 只接受 `replicas` = 1 或 8（[`render_formal_target_language_speech.py:385`](../../scripts/render_formal_target_language_speech.py)）；16×4 在 Spark 上触发过内存保护 | 一个语言任务就要能放下 8 个副本：显存估 40–88 GB（未实测），主机内存估 64 GB 以上。**80GB 卡只是候选，上限估计会超**；租卡前先测每个副本的 CUDA 峰值（`torch.cuda.max_memory_allocated`）。超过约 70 GB 时改用 H200 141GB。“每语言拆到两张小卡”目前做不到：renderer 只接受一个 `device` 且 8 副本 preset 固定 `cuda:0`，同一语言目录又有单写者锁；要先实现按 GPU 分片和产物汇总，才能算作备选 |
| L3 回转写 ASR | 每个任务 1 个驻留模型，batch 1–8 | 没有多副本 pool；目前整轨渲染完才开始筛查 | 和同语言 TTS 同卡，额外约 2–4 GB |
| L3 跨语言 | zh / ko / es 各一个渲染任务 | 没有跨任务的 GPU 调度器；两个 8 副本任务放同一张卡会互相抢显存 | **一个语言任务占一张卡**。三语同时跑就是 3 张卡 |
| L2 文字 | 组 worker，API 调用 | 默认每个 run 1 个 active locale；显式 execution-v2 冻结并发配置时最多 3 个（见 [controller 合同](../canonical-layer2-controller.zh.md)） | 走 OpenAI API，不占 GPU。只有改用本地文字模型时才需要 GPU：16 路并发估需 1 张 H100 跑 vLLM，且质量未批准 |
| Sunday live | 现场字幕 | 独立 `live_session`，要求现场设备 | 不在本方案内，继续本地 |

### 三语同时开跑是常态

10/4 三份口语候选分别在 08:57、09:31、09:44 ready，但用的是**同一张批准收据**（10:13，见 [交接与发布复盘](20261004-retrospective/handoffs-and-release.zh.md)）。批准一到，三个语言同时可以渲染；当时只是串行排队，韩、西各多等了 22 和 44 分钟。L2 execution-v2 也允许三语同时生成文字。所以按“批准即派发”，**常态就是 3 个渲染任务同时跑**，要按 3 张卡规划；只有改成逐语言批准时才会错开。L3 超窗回 L2 改译文后的重合成只是局部单元，量小。

### 关键结论：并发几乎不改变成本，只改变“开几张卡”

每周 GPU 总工作量大约固定（估 0.75–1.25 个 H100 卡时）。三语串行用 1 张卡跑约 35–55 分钟，和三张卡各跑约 11–18 分钟，卡时差不多（并行多付两次开机），费用接近；差别在于墙钟和闲置。真正浪费钱的是**为了并发长期开一台多卡机器，等人工批准时也在计费**。

## 推荐方案（按并发修订）

以下方案都假设本周是新建的单讲员任务（周日常态），能用 8 副本 preset；多讲员周次按 1 副本跑，不需要 80GB 卡。

### 方案 A（推荐）：每个语言一张按需大显存卡，批准即开

- 规格：每个语言任务 1 × H100/A100 80GB（先实测显存；不够就 H200 141GB），GPU 云上按 16 vCPU、64–96 GB 内存、100–200 GB 盘配置。GCP 的 A100 是固定规格：`a2-ultragpu-1g` 为 12 vCPU、170 GB 内存，不能自定义。共同批准时同时 3 张。
- 触发：语言文字批准收据一到就开卡，渲染 + 回转写完就关。
- 平台：Modal / RunPod Serverless（按秒计费，最贴合），或者每任务开一台按需 VM。授权音色 checkpoint 放私有卷，避免每次重新下载。
- 每语言耗时（估，按上面的计时模型）：1 小时证道约 11–18 分钟（含开机和装模型）。三语共同批准后，约 11–18 分钟三语都可听。
- 月成本（估，每月 4 篇）：每张卡计 15–25 分钟（含一次重试余量），3 张即每周约 0.75–1.25 卡时，每月 3–5 卡时。GPU 云按需 H100 约 $2–3.5/卡时：约 $6–18/月；serverless 约 $4–6/卡时：约 $12–30/月；GCP A100 约 $5–6/卡时：约 $15–30/月；另加约 $5 存储。
- 配额与开机方式：要确保同一时刻能拿到 3 张 80GB 卡。GPU 云要确认区域容量。GCP 的 `a3-highgpu-1g/2g/4g`（1–4 张 H100）按官方文档只能用 Spot 或 Flex-start，不能普通按需开机：Spot 可能中途被收回，Flex-start 可能排队，所以上面的“批准即开、11–18 分钟可听”在 GCP H100 上不成立，除非接受续跑和排队。GCP 上要“批准即开”应选 A100 80GB（`a2-ultragpu-1g`，可按需），配额默认常为 0，要提前申请。

### 方案 B：每周开一台 2 卡 80GB 机器

- 2 × H100 / A100 80GB；GPU 云上按 32 vCPU、192 GB 内存配置，GCP 则是固定的 `a2-ultragpu-2g`（24 vCPU、340 GB 内存）。两种语言并行，第三种排队，最晚一个语言比方案 A 多等一轮（估 8–13 分钟，第二轮不用再开机）。
- 只开一台机器；但第二轮只用一张卡，另一张闲着也计费。而且 renderer 只认 `cuda:0`，同一台机器上的两个语言进程会都挤到第一张卡上，派发器必须给每个任务单独设 `CUDA_VISIBLE_DEVICES`（或容器 GPU 隔离），否则第一张卡显存不够、第二张闲置。
- 月成本（估）：两轮共约 25–40 分钟（含一次开机和重试余量），2 卡计费，每周约 0.8–1.3 卡时，每月 3.5–5.5 卡时。GPU 云 $2–3.5/卡时约 $7–19/月；按 $6/卡时上限约 $33/月；GCP `a2-ultragpu-2g`（约 $5–6/卡时）约 $18–33/月（GCP 的 2 卡 H100 同样只有 Spot / Flex-start）。卡时和方案 A 接近，差别主要是第三种语言多等一轮。

### 不推荐：GCP 单张 L4，或 3 卡 / 8 卡常开

单张 L4 放不下 8 副本，跑不了现在的正式 preset。常开多卡机器（例如一台 H100 全月 730 小时）每月 $1,500 以上，完全不划算。

## 仓库里需要改的地方

1. **镜像**：Spark 是 ARM/GB10，云 GPU 基本是 x86。需要一个 linux/amd64 CUDA 镜像，锁定 PyTorch、Qwen TTS/ASR 依赖，不能复制 Spark 的 venv。
2. **派发**：`spark_speech.py`、`run_weekly_dubbing.py` 和 [正式 renderer](../formal-layer3-renderer.zh.md) 的 `--spark-production` 都假设 Spark 主机（SSH/Docker 路径固定）。需要一个云 GPU 后端，或者一个通用的“远端 CUDA worker”适配器。
3. **内存保护和副本数**：8×8 入口用 Linux `MemAvailable < 24 GiB` 当保护，这是针对 Spark 统一内存设计的。独立显卡要**在保留宿主内存保护的同时**再加一道 GPU 显存保护（`torch.cuda.mem_get_info`）：8 个副本进程和回传的音频窗口仍占宿主内存，显存够不代表主机内存够。如果想用 48GB 或更小的卡，要放开 `replicas ∈ {1, 8}` 的限制（例如允许 4），并当作新的执行身份重新验收。
4. **跨语言并发调度**：现在没有跨任务的 GPU 调度器。云端按“一个语言一张卡”就不需要它，但需要一个小派发器：语言批准收据一到就开卡、跑任务、回传产物和收据、关卡；卡数上限设为 3。如果同一台机器上有多张卡（方案 B），还要为每个任务隔离一张 GPU（`CUDA_VISIBLE_DEVICES` 或容器 GPU 命名空间），因为 renderer 固定用 `cuda:0`。L2 controller 的“同 run 一个 active locale”限制不影响 L3，但会限制上游文字批准的节奏。
5. **执行身份**：按 [计算策略](../local-production-compute-policy.zh.md)，换设备/精度就是新的执行身份，云端产物不能和 Spark 产物拼成同一个 render。现在单元 intent 只记录逻辑设备 `cuda:0`、精度、checkpoint 和 renderer/pool hash，不记录后端、GPU 型号、主机或云运行时，所以只换目录不够：`--reuse-from` 仍可能把 Spark 产出的音频当作同一 intent 收进云端 render。接入云端之前，要先把后端/运行时身份版本化地写进单元 intent 和 receipt。三语同时在云端跑也需要每语言独立任务目录。
6. **策略文档**：现在写的是“Spark 默认、MacBook fallback”。加入云端需要 Jony 决定，并更新这份策略和 `AGENTS.md`。
7. **模型和凭据**：授权音色 checkpoint 只能放私有存储（不能上公开 Hugging Face）；云端的 API key 用平台 secret，不进 Git 和日志。
8. **媒体取得**：项目曾在 Cloud Run 遇到 YouTube bot-check。来源下载继续在本机做、再上传，最省事。
