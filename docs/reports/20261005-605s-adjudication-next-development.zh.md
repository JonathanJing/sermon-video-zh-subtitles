# 605.5 秒样本：来源裁定后的下一轮开发

依据[本轮实测](20261005-gemini-605s-api-diagnostic.zh.md)、[四层合同](../multilingual-production-interfaces.zh.md)及[既有恢复规划](20261005-production-findings-next-iteration-plan.zh.md)。这是开发顺序与验收清单，不代表这些功能已实现，也不把诊断收据当作正式批准。

## 先分清三类故障

| 类别 | 本轮证据 | 正确动作 |
|---|---|---|
| L1 来源事实／句界 | `0-u076` 的 “You're filled in the middle of a trial” 在简中、韩语、西语 `g021` 均触发语义疑点；`0-s125` 的 `0-u148/149` 未完从句切点被英文机器裁判判为 fail | 导出绑定媒体 hash、窗口和词时间的短音频及前后句，记录人工对原话和切点的裁定。若改英文或锚点，生成新版 L1；全部 locale 的正式下游身份失效，不能沿用旧人工批准 |
| 引文边界／目标语言证据 | 简中 `g018/g029`、西语 `g024/g026/g040` 报引文或疑似引文缺固定版本、来源核验或使用状态；`g021` 也涉及引文性质。准备脚本目前只为 `g018` 的 `0-u067/068` 冻结了 **pending** 的诊断引文 | 在付费翻译前穷举候选引文，逐处裁定直接引文、转述或典故，绑定英文偏移／来源、目标 locale 的版本与完整句措辞及使用状态。不确定处明确阻断，不把试译稿改标为已审引文 |
| 模型输出格式与运行恢复 | r15 的复核 `evidence` 为字符串数组；r17 韩语 `g018` 初译返回对象式 utterance；CLI 24 槽出现 403/unknown，API 4 槽完成 191 次新请求并复用 111 份响应 | 已做严格格式适配和诊断 API 响应复用，但对象式适配尚未跑第三轮真实回归。格式失败、内容 fail、调用 unknown 要分型；不能因格式修复消除内容 fail |

## 建议实现顺序

1. **P0：裁定包和付费前阻断。** 为 `0-u076`、`0-s125` 和所有候选经文生成一个可复查队列：来源音频切片、文本前后文、词时间、媒体／窗口／锚点 hash、各模型分歧、待决定字段。裁定收据逐项记录原话或边界、引文性质、版本／精确句及适用 locale；`pending` 不升级为通过。扩展 `prepare_next_concurrency_test.py` 与 `target_language_rule_preflight.py`，使 `source_bound_exact_quote` 下缺证据的组在**首个付费请求前**失败，同时不阻止无关准备工作。验收：含当前 g018/g021/g024/g026/g029/g040 的零调用负例；来源或偏移换字、缺一 locale 版本、伪造状态均拒绝。
2. **P0：诊断链的分组修订与跨轮恢复。** 正式 runner 已有绑定失败缓存 SHA 的 partial-repair brief；诊断链却禁止 repair／cross-run cache。新增隔离的诊断修订 attempt：内容 fail 仅对受影响组发**新的初译→独立复核→语言插件**，成功邻组仅在 payload、规则、模型／项目及上下文完全相同且原响应终态已确认时复用；unknown 持槽等待对账。新计划引用旧收据，不改写 r15/r17。L1 身份变化先生成失效／复用计划，不能直接沿用旧候选或批准。验收：一组修订只新增其规定调用；旧失败仍可审计；改来源和规则时精确拒绝不安全缓存。
3. **P0：失败分型及依赖调度。** DAG 目前把失败节点写成终态并停止后续派发；Gemini 只返回概括性 `attention_required`。加入机器可判的 `schema_invalid`、`content_needs_adjudication`、`provider_unknown`、`capacity_wait`，区分全局 L1 阻断与单 locale／单组阻断。监督模型只汇总证据、提示人工，不决定批准、重试或释放资源。验收：一个 locale 的确定内容 fail 不取消已运行的独立 locale；共享 L1 改动阻断所有正式下游；同计划不重发终态失败节点，修订使用新 attempt。
4. **P1：后续层接续与质量回归。** 先用明确标记的 mock 人审收据验证 L2→大纲／默想→L3→L4 的机械依赖和恢复；这只能证明调度。待来源和引文裁定后，用同一 605.5 秒真实模型链重新取得每个 locale 的 machine pass、插件／candidate、人审、自然语速音频、完整听审与同步证据，最后按原 release plan 发布并分别做 HTTP、iOS Beta 播放和设备验收。测量总墙钟、各层等待、实际 API/CLI token 与成本、复用量和质量；不把局部 197–205 秒的失败节点耗时当端到端提速。
5. **P1：运维恢复收口。** 本轮 Spark 排他恢复被抢占前的旧 `queue.json` 观察状态阻挡，需手工保存快照、清理陈旧观察记录后才恢复服务。把这个过程变成有版本的中断／恢复收据与原子恢复动作，并核对原 `job_pipeline`、`x_watch_pipeline` 是否从已有产物续行；API／CLI 的未知账单与队列任务状态分别对账。验收：真实服务健康与原任务恢复读回，重复 `finish` 幂等，任何未知活动调用都不自动重发。

## 顺序边界

P0-1 的裁定先于新的 605.5 秒付费译审。P0-2 可先用离线响应和一组小额 dev 请求开发，不需要等待裁定；但内容 fail 不能靠该机制自动放行。当前 `tongxing-dev` OpenAI API 路线只在本次诊断中实测；[正式模型策略](../production-model-runtime-policy.zh.md)仍以 Codex CLI 为文字默认并关闭自动 API fallback。若要将 API 并发路线升为生产默认，应另行版本化策略、预算与费用准入、项目身份和正式端到端验收，不能由诊断开关隐式完成。
