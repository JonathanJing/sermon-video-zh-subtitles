## 复盘判断

1. 对话总量主要来自长上下文被反复读取，不能把 9.19 亿理解为生成了 9.19 亿新文字。主对话与子 Agent 的重复上下文仍会产生真实请求用量；缓存命中高不等于零成本。
2. 翻译、口播与配音准备窗口占约 47.7% 的 Codex token。它包括探索、源身份/术语重绑定、规则修复、审核与调度；仅凭窗口总量还不能量化每一种原因贡献多少。
3. 三个早期复用 Agent（iphone_review_options、rebind_scripture_v4、rebind_terms_v4）合计约 3.32 亿 token。后续独立短任务更适合只传冻结输入、明确产物和证据路径；当前并无对照实验，不能宣称缩短上下文必然节省多少。
4. 主对话 32 次上下文压缩，说明工作跨度与上下文负担很大。将生产状态、恢复点、审查队列移入持久化执行状态，可减少对话重复检查；需要用同样质量目标的对照运行验证收益。
5. 会话时长、任务区间、GPU 执行时间、人工听审分别计量。后续若要比较速度或额度，必须固定统计窗口、任务范围和账本，不能从 token 总量直接换算额度百分比或费用。

## 验证与限制

逐 response 去重、输入+输出=total、主+子=总计、八个时间窗口=总计。主累计回退与逐记录汇总差异已显式记录；未把它静默消除。统计来自冻结时间窗，本次审计的新请求不在数值中。完整本地聚合为 `timing-token-audit-v1/codex-dialogue-audit.json`；不上传原始 Codex 会话。
