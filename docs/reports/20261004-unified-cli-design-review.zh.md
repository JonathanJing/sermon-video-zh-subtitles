# 统一 CLI 设计审核

日期：2026-10-04（洛杉矶时间）。审核对象是 PR #242 中、提交 `f16007a53932eb5cce9673b1bad084ac76201f7d` 的 [统一 CLI 与持久化执行设计](../unified-cli-pipeline-design.zh.md)。原稿 SHA-256 `1cea7a50f3bdd83dd76c356a9b9bc89aabf3136d564026746591e9ddab5288fc` 保持不变。本文只记录审核结论，不实现命令，也不宣布提速。

对照材料有两份。一份是同日的 [每周流程改进分析](20261004-weekly-production-flow-improvements.zh.md)，覆盖 2026-09-23 至 2026-10-01 的报告。另一份是设计自己钉住的 [播客 Layer 1–4 复盘](20261003-podcast-layer1-4-retrospective.zh.md)。设计正文里的 17 小时 41 分 33 秒、L2 累计 6924.057 秒、ES/KO 错源 5 轮 3362 次调用和 553.639 秒，与该复盘一致。

## 审核结论

设计的实施顺序是对的，而且和已经发生的返工对得上：先挡住错源和无效付费，再给已有 durable job 一个常驻 owner，然后才提高并发。它没有把 Prefect 做成第三套生产调度，也没有用交接 p95 代替整周墙钟。这些边界应保留。

它还没有把几类已经让人重新授权的失败写进预检夹具，也还没有把「页面就绪后结束生产会话」写成验收。已明确的完整目标包含大纲、默想和双端正式内容发布；首轮 canary 可经授权缩小验证范围，但不能由技术审核更改最终目标。下面的发现按这个差别排列。逐步落到 CLI 和每一生产步骤的改法见[分步改进](20261004-unified-cli-step-improvements.zh.md)。

## 发现

### F1：预检夹具还没覆盖已经关闭整次运行的失败

1.2 的验收写了错源 ES/KO、过期审核、政策冲突和插件拒绝，并且要求 `newPaidRequests=0`。这些该做。10 月 1 日监督续跑里，还有一批失败发生在模型调用之前，并且每次都关闭父运行、要人开新授权：读取器 256 KiB 上限、延迟加载模块改变代码身份、`sox` 导入、DAG 漏字段、子进程内查 Git。同月新鲜重跑在三语音轨已经可播之后，把 `adapterSha256` 和 `executionHost` 当成 MFA 内容变化。

1.1 写了「只改路径不产生重复付费身份」。1.3 把代码漂移定义成停止新派发。7.1 把 `hostId` 放进事件。三者还没有合成一条验收：主机名和临时路径可分列为 provenance；adapter 实现哈希不能一概降为 provenance。媒体、窗口、文本和稳定依赖没变时保留内容与既有批准，但代码/执行准入仍须完整身份核验和明确兼容规则。未知依赖和被改过的文件继续拒绝，具体 App 闭包负例见追加审核 N2。

另外两条应进入同一预检，而不是等第一组付费返回：prompt 与 schema 不一致时第一组失败后停止其余组；派发前拒绝保持 `blocked`，不把尚未产生 reservation 的尝试记成已关闭的付费父运行。manifest 未变时，这种拒绝不要求新的预算确认。

### F2：复用计数要能对上 r12，不能只看 `cache_hit`

中文 r12 在 24 并发下用 79.150 秒补齐 237 组，并复用 602 组，但 `cacheHits` 为 0。9 月 29 日的 runner 则相反：传入复用目录时，尚未执行的组也可能被标成命中，随后仍然发出新请求。

5.4 的断网、空 key 恢复验收要保留。再加一对夹具：真复用必须给出 `reused_groups` 与 `fresh_api_attempts`，不能把 602 隐藏成 0；只传复用目录、该组没有命中响应时，命中标记必须为假，并且能看到新请求。7.4 已要求 cache token 不当作新文本，这里补的是计数本身。

### F3：页面就绪后要结束生产会话

设计要求正常步骤不再由 Codex 选择下一条命令，8.1 要求 happy path 的 `runtimeCodexTurns=0`。播客和 9 月 20 日的大头都是长会话反复读入缓存上下文，而且页面或资源交付之后，工程修改仍留在同一窗口。Luna 与业务账本的 response ID 没有交集，说明编排 token 不是翻译 token。

建议在 8.1 增加一条，不改现有 p95：到达 manifest 里的 `completionScope` 后，owner 不再为该 run 派发生产阶段；随后的代码、文档和海报使用新的任务，只接收发布收据和证据引用。Agent 若仍参与歧义决策，输入保持有界状态包。9 月 29 日提出的 32 KiB、最多 16 条证据引用仍是待验证上限，可以先当作工程预算。10 月 1 日只读 Agent 约 60 秒后仍返回证据不足，因为包里没有字段级比较。在能指出「差的是 `adapterSha256` 和 `executionHost`」之前，不要把实时诊断 Agent 放进 owner。

附录里 `job wait --timeout 30` 会鼓励会话每 30 秒读一次状态。wait 超时不取消 job 这一点是对的。给人和 Agent 的默认示例应是等到 `human_pending` 或完成事件，而不是在变长的上下文里轮询。

### F4：首轮 canary 可缩范围，完整产品目标不得由审核改写

4.8 把大纲和默想做成真正的生成与审核，并写入 4.9 的 candidate set。当前 App producer 只复制已批准资产，设计把这件事写清楚了。每周痛点是译文、配音、听审和页面。把两项新的模型产品放进默认完成范围，会在单语 canary 证明预检和 owner 之前增加付费和人审。

4.10 的 `dual_production_verified` 要求 iOS 正式与 Firebase 正式都完成。设计允许一端失败时保持 partial，也允许首轮把 canary 的 scope 缩小。仅经明确批准的首轮 canary 可选 Firebase reader 等较小 completionScope；这不能成为修改每周完整默认目标的授权。已明确的最终 App 页面及翻译、配音、大纲、默想、双测试端人审后双正式端内容验收保持不变。设备/现场/PDF 按各自约定独立记录；内容晋级不等于每周发布新的 App Store 二进制。缺前提时按实际 scope 保持 pending/partial，不自称完整成功。

### F5：人审收据入口还没有审核队列

2.3 拒绝用布尔值和自由文本伪造批准，这要保留。`review ingest` 假定收据已经存在。播客的 ASR 待审是中文 38、西语 53、韩语 45 个单元，全文听审仍然是放行条件。9 月 24 日的远程桥只完成一次 `mock_ping`，领取器不是常驻服务。审核表还曾把时间基准加错，导致同一次窗口批准被再确认。

4.5 已经会生成 worksheet。建议它同时产出可提交的队列：插件失败、Sol 标出的组、ASR 疑点、超时单元，以及未改单元的原收据。音轨时长变化后的整轨听审继续保留，因为一句的时长会牵动后面的字幕。身份未变的批准不重复索取。远程审核可以后接，但 ingest 不应是人必须守着生产会话才能完成的唯一步骤。

### F6：三语并行保持在测量之后

现状是 canonical L2 每个 run 至多一个 active locale，一次 tick 至多派发一个 durable worker。6.4 把「已批准语言的 L3 与另一语言的 L2 重叠」放在 P2，并要求质量、失败率和预算不恶化。播客里 ES/KO 的 24 并发是依次执行的，而且有一轮打在错源上。先做单语 canary，再谈三语重叠，和这段证据一致。

不要把「现在没有三语同时跑」提前到 P0 去改并发。P0 仍然是 F1 的预检和 F2 的复用计数。6.3 用完整 419 段做 cold/warm，也不要用 64 段中位数外推，这条保持。
