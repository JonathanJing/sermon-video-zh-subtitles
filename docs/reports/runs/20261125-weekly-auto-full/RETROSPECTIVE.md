# 复盘：20261125-weekly-auto-full

数据见同目录 INDEX.md 和 manifest.json。这是周六自动流程在生产机 mbp16 上的第四次演练，也是第一次整篇长度的运行：第 11 周证道（2026-11-21 正式播放版，35 分 39 秒，470 句）从英文表批准一直做到三种语言的整轨听审，中途还演练了一次「听审退回 → 自动改句重配 → 重新打开听审」和一次驱动重启后的续跑。前三次见 `20261125-weekly-auto-rehearsal`、`20261125-weekly-auto-paid-transcription`、`20261125-weekly-auto-tracks-40`。

## 结论先行

- **交付类型**：测试（演练），不发任何通知。没有页面、没有发布。
- **最终状态**：生产目录 `outcome.json` 为 `rehearsal_complete`，exit 0。三条音轨都在第一次合成后通过同步闸门，没有触发整条重配。
- **证据边界**：两个 Layer 1 决定、中文音轨的一次「要求修改」和最后三个听审决定都由代理直接写入，备注写明是演练；没有人听过任何音频，也没有人读过译文。听审结论文件的 `verdict` 是 `rehearsal`、`humanApproval` 为 false，不能用于发布。同步数值是脚本量出来的，不是听感结论；译文质量只做了抽样对照（见下），不是审校。
- **这次回答了什么**：整篇长度能不能一口气做完（能）；要多久（英文表批准后 47 分钟出第一条音轨，1 小时 57 分钟三条都可审）；Opus 并发会不会被限流（6 路并发、约 20 次调用，没有）；内存够不够（全程可用内存不低于 21.6 GiB）；中途重启会不会坏（不会）；听审退回后的自动改句重配在真实数据上是否可用（可用，5 分钟出第 2 版）。
- **没有覆盖**：人在手机上听整轨；真实（非演练）运行里带已批准英文包的预检（只做了不落盘的开工计划检查）；同步闸门不过、要精简并整条重配的情况；改句之后闸门不过的情况；发布、声音定位、海报。

- L3：三种语言的配音、合轨、同步闸门、整轨听审页（从另一台 Mac 经 tailnet 打开了中文第 2 版，470 句，改过的句子带标记和改动前后的文字；音频和视频文件能按范围请求取到）。中文那条走了一次改句重配：一句照听审人给的改法替换，一句只说了哪里生硬、由 Opus 只改那一处，一句只重配；改句前后逐句加速的结果相同（92 句、省 51.56 秒），最大落后不变。最后三个听审决定由代理写入（演练）。
