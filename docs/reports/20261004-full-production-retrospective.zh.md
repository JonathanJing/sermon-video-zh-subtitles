## 1. 版本变化到底触发了什么

所有保存的L2请求中英文sourceUnits与anchor hash一致。v6/v7→v8的source package hash变化来自人审绑定与上下文策略，审计明确 `englishWordsAndAnchorsUnchanged=true`。它不是英文又重写一遍，也不自动证明必须整批付费重跑。

Astra翻译／Sol复核的角色与promptVersion大体保持固定，但model-facing术语、引用规则、修订指令和上下文改变了实际payload。审计因此核对完整requestPayloadSha256及策略内容，而不单看目录版本号或promptVersion。

| 关键转换 | 实际变化 | 新调用／复用含义 |
|---|---|---|
| v6西语／中文 partial repair | u018限速语义、u026代词上下文；先前提前失败 | 只少数组是修复，大部分新调用是补未完成结果 |
| v6→v7韩语 | 人确认的术语／policy变化，英文不变 | 新948次；未保留证明全部组均受影响的分析 |
| v8中文revision-2 | 引文映射只存在deterministic plugin，模型没收到 | 新948次，4,095,663 token |
| v8韩语revision-2 | 排除英文未口述的编辑式经文引用 | 新948次，2,377,431 token |
| plugin-only三语迁移 | model-facing输入一致，仅插件实现修复 | 每语948角色结果复用，均0新增API |
| 韩语revision-3／西语revision-4 | 术语、转折、数字上下文定向修复 | 各6／2新调用，其余942／946复用 |
| 口播候选与实测时长修订 | 源与最终policy不变，修订组与修复输入改变 | 记录changedGroups和carried_forward，不能称旧缓存无效 |

完整34轮表、身份和原因证据见 [版本与缓存专项](20261004-retrospective/versions-and-cache.zh.md)。应先冻结模型实际消费的术语／引文策略，再生成结果；source package封装变更应分别比较内容身份与审阅绑定，不能绕过必要审批，也不能只凭新目录名清空缓存。

## 5. Spark、8×8和恢复

首轮三语串行，各renderer进程约22分钟；它不是纯GPU时间。后续中文／韩语各约21分钟的62秒重组只复用474句，新增synthesis为0。参数含cuda不代表再次调用GPU模型。

西语14:04–14:19修订attempt在已有288复用+32新生成后失败；14:20、14:25实际stderr都指向主机MemAvailable reserve guard。失败时可用内存未落盘；GPU数据N/A，峰值unknown。没有证据定位某个共驻留服务是根因，也不能用清理后的free快照倒推失败时峰值。

17:19–17:41西语同输出续跑闭合为320句既有commit+122句外部复用+32句新合成=474，随后仍有尾部排程问题。8个worker ready证明该次pool加载；batchSize8不是64句始终同时运行的证明。尾事件不足以求每worker吞吐、GPU利用率或可比较的失败率。

需补guard瞬间MemAvailable、RSS／容器归属、共享内存、worker提交／返回、exit reason及阶段起止。只在真正基础设施失败时恢复／降级，内容或身份失败仍留在原层修复。

## 8. ASR疑点与人工裁决的证据缺口

最终筛查各474句，中文33／韩45／西38项requires_review，阈值0.88。韩西83项都有逐group／audio／text身份绑定的approved，但依据是同一次整体用户听审放行，没有逐项正确转写或错误类型。
