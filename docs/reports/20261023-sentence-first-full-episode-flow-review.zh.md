# 复盘：逐句优先整期生产流程的瓶颈与改进（2026-10-23）

时间一律为 PDT（UTC−7）。时间点来自本会话的队列输出、Spark 任务日志、产物文件时间与用户消息；没有日志的环节标“约”。运行数据、收据与审核结论见同轮运行报告 [PR #1333](https://github.com/JonathanJing/sermon-video-zh-subtitles/pull/1333)；本轮代码与 Registry 改动见 [PR #1334](https://github.com/JonathanJing/sermon-video-zh-subtitles/pull/1334)。

## 结论先行

- 交付：59:15 的《If I Had More Time — Jesus promises》整期，946 句，Steve Bang Lee + Eric Geiger，三语 zh-Hans / ko / es，以 `human_reviewed` 发布到正式站（最终 Hosting 版本 `25986755c1843f5b`）。
- 总墙钟约 3 小时 35 分（12:15–15:50）。其中机器计算约 2 小时 45 分（TTS 111 分钟、说话人区分 52 分钟、翻译约 12 分钟、发布约 12 分钟），其余是三次人工听审和英文/映射确认的等待。
- 最大计算瓶颈是 **TTS 串行队列**：一个 Spark 独占会话一次只跑一个任务，zh/ko 各 1.36× 实时，es 用 batch-8 后整体 2.68×、batch 段 3.87×；正式 8×8（8 副本）只支持单讲员，双讲员用不了。
- 最大人力瓶颈是 **人工听审**：三条 60–67 分钟的轨、审核表 211/171/184 行标记，用户实际 15–21 分钟给结论，但流程要求听完整轨；现在的 CSV + 整轨 MP3 不是听审工具。
- 最便宜的可靠性改进是 **preflight**：Eric 的 `speakerId=eric_geiger` 与 checkpoint 内部 key `eric_pilot` 不一致、英文包证据是相对路径，这两次停顿都能在开工前拦住。
- 结构性缺口有两个：SRT 派生 Layer 1 的英文质量（这次靠人工英文审核兜底）和双讲员 8×8；前者影响质量，后者影响下一轮的 TTS 墙钟。

## 瓶颈（按实际影响排序）

### 1. TTS 串行队列（计算，最大）

一个 Spark 独占会话一次只接纳一个任务；三语 × 两讲员排成一条队列。zh/ko 各 1.36× 实时，es batch-8 整体 2.68×、batch 段 3.87×。正式 8×8 的 8 副本路径明确拒绝多讲员（[双人播客制作规范](../podcast-dual-speaker-production.zh.md)），所以这次只能用逐句线的单副本 batch-8。**若 zh/ko 也用 batch-8，TTS 墙钟预计可从 111 分钟降到 55–65 分钟（估算，未实测）。**

### 2. 人工听审（人力，最大）

三条轨 60–67 分钟；审核表 211/171/184 行标记（ASR 低分、讲员存疑、复核修订混在一起）。用户实际 15–21 分钟给结论，但流程要求“听完每条整轨”；这段时间是硬等待，且不可压缩到零。当前交付物是 CSV + 整轨 MP3：要自己找句、对时间、判断同音误报。**问题不是用户慢，而是工具没有把“要听哪几句”变得便宜。**

### 3. 说话人区分（固定成本）

Mac CPU 上 52 分钟（占墙钟 25%），串行；脚本是临时写在 `artifacts/tmp` 的，正式 producer 不在仓库；72 句占比 <0.8 需要人确认。每集都会重复这 1 小时，而且没有预检能发现“音频太短/太长/没权限”。

### 4. SRT 派生英文（质量与返工）

滚动字幕造成零时长、句间重叠，切片失败两次；英文是 ASR 质量（人名、句子边界、标点都需要人看），这次靠你逐句英文审核兜底。它比正式 Layer 1（ASR + MFA）快，但把质量风险推给了英文审核和翻译；英文包还是这次临时写的，不是正式 producer。

### 5. 发布的三次部署与路径假设

资产 → release + 目录 → 英文对照，三次部署。英文 builder 因为包内证据是相对路径、从 worktree cwd 解析不到而失败一次。第三次部署在 release 上线后做是保守的；stage2 快照里其实已经有 release/文稿/字幕的哈希，理论上可在 stage2 上生成英文对照、随第二次部署上线，省一次往返。

### 6. 集成摩擦（每次停一下）

- Eric 的 `speakerId=eric_geiger` 与 checkpoint 内部 key `eric_pilot` 不一致，首次 TTS 33 秒失败，重建 speech。
- AGENTS 引用的 `speaker-checkpoints.dgx.json` 不存在，checkpoint 路径靠 `ssh test -d` 逐个确认。
- 英文包证据相对路径。
- Registry 的“授权用途”和“语言能力”是两件事，更新时容易被当成一件事；这次先在 file 里改用途，等三条轨通过后才改能力状态。

这些都是可预检的，不是能力问题。

### 7. 翻译跨子代理一致性

12 个子代理（会话上限 8，es 分两波）；韩语出现 `당신/여러분` 混用，世纪/数字写法各份不同；复核修订 120/93/102 句。并行换速度，代价是合并后的统一性。子代理这次自发做了交叉核对，但没有固化成步骤。

### 8. ASR 误报与审核分诊

西语 ASR 均值 0.959、65 句 <0.85；大量是 `Guau/Wow`、`Sí/C` 这类同音，不是配音错读。审核表把“ASR 低分”和“真问题”混在一起，浪费听审注意力。

### 9. 运行报告与计时

导出器只拿到日志，没有 journal/timings/outcome；复盘靠手写和回看消息时间戳。每轮的时间构成无法自动比较。

### 10. 产物与清理

上一轮为腾空间删了 416 GB 的 TTS/ASR 中间产物，只留小表；这一轮保留了整轨、TTS、ASR 和审核表。清理策略仍是手工的。

## 改进（按优先级）

### P0：下一轮就能做，收益最大

1. **全语种 batch-8（整期）+ 逐句修复仍 batch-1。**
   es 已有 2.68× / 3.87× 实测；建议 zh/ko 也默认 batch-8，修复时按 8 句窗口重合成，并在 run.md 记录 batch 窗口与成员哈希。需要接受“改一句重配 8 句”的身份代价。预期 TTS 111 → 55–65 分钟（估算）。
2. **一个 `sentence-first preflight`。**
   一次性检查：run 目录/cwd、`speakerId → speakerKey → checkpoint` 解析、Registry 授权与能力、英文包证据绝对路径、Spark 会话、Firebase/ADC。Eric 的 33 秒失败、英文对照的相对路径失败都能提前拦住；这是最便宜的可靠性改进。
3. **HTML 听审播放器。**
   按句切音频、点句跳转、标出 ASR 低分/讲员存疑/复核修订、逐句写结论并直接落成收据。现在的 CSV + 整轨 MP3 让人自己找位置；播放器把“听审”从 60 分钟压到 30–40 分钟（估算），而且结论直接可追溯。
4. **SRT 规范化器进仓库。**
   零时长、句间重叠、滚动重复、名称修正、句界/停顿检查一次做完；把这次的三次切片失败变成一次预检。英文审核仍需要人，但不用在切片的错误上返工。

### P1：结构性改进

5. **双讲员 8×8。**
   要么扩展正式 renderer 支持按讲员分路，要么在逐句线做“同语言两讲员共用 8 副本池”。这是继 batch-8 之后最大的计算收益；需要先确认 GPU 内存（正式 8×8 实测最低可用 38.43 GiB）与批次身份。正式 8×8 单讲员的 419 句约 6.2 分钟热 TTS 是组件外推，不代表整篇。
6. **英文对照并入 stage2（两次部署）。**
   stage2 快照已有 release/文稿/字幕哈希，英文 builder 可在 stage2 上生成，随第二次部署上线；保留“release 上线后必须回读”的检查，但省掉第三次往返。先在 Dev 页验证合同再改正式驱动。
7. **翻译一致性的后处理。**
   每期一份共享术语/称呼表；合并后跑一次“人称/称呼、世纪写法、人名、数字”的统一检查；子代理上限 8 时分两波，但用同一份 brief 和已合并的相邻部分做交叉核对（这次子代理已经自发做了，应固化成步骤）。
8. **ASR 分诊。**
   换更大的 ASR 或对同音/数字做规则归一；审核表把“同音误报”和“需要人听”分开，播放器只推后者。

### P2：文档与流程

9. **AGENTS/runbook 补上这次的四条。**
   SRT 派生 Layer 1 的句表检查、`speakerId → speakerKey` 解析、batch-8 的身份与修复窗口、英文包证据路径；加上“多讲员 8×8 仍缺”的明确限制。前一轮的环境/讲员回退/checkpoint/Dev/英文片段/产物保留已在 [PR #1330](https://github.com/JonathanJing/sermon-video-zh-subtitles/pull/1330)；这一轮的在 #1334 与 #1333。
10. **计时与报告。**
    给逐句脚本加 journal/timings/outcome，导出器就能自动出总时间、TTS 速度、审核等待；复盘不用靠消息时间戳。

## 证据边界与未验证

- 时间点来自会话队列输出、Spark 任务日志（UTC 转 PDT）、产物文件时间与用户消息；TTS 墙钟取自 `tts-log.jsonl` 的 `wallSeconds` 之和，队列窗口含模型加载与 ASR，故两者略有差异。
- “预计可降到 55–65 分钟 / 听审 30–40 分钟”等是估算，不是实测；es 的 2.68× / 3.87× 是实测。
- 发布侧证据：12 个资产 HTTP/SHA、MP3 Range 206、目录与 release 回读 6/6、英文对照 946 blocks/语言；iOS 真机/TestFlight、浏览器播放、现场验收 `not_run`。
- 运行报告的收据与脱敏数据见 #1333；本文件不复述收据哈希。
