# 每周复盘 为什么一篇证道的制作用了 1.69 亿 token

一段约 32 分钟的英文证道，从收到制作指令到最终页面核验，花了约 5 小时 47 分钟。负责监督制作的 Codex 主任务和三个子任务，累计记录了约 1.69 亿 token。

这是我们 9 月 20 日制作记录中的数字。当我们通常只有 10–12 小时，要在下一场证道开始前完成交付时，这样的制作时间已经占掉了窗口的很大一部分。

我们做的是一个帮助会众跨越语言障碍的个人项目：把英文证道做成可以阅读、收听的中文内容，后来又扩展到韩语和西班牙语。交付前，需要确认视频、整理原文、翻译和审核、生成配音，再检查它能不能跟上原视频。

这次复盘，我们想回答两个问题：为什么用量会变得这么大？接下来，怎样让每周制作少一些反复折腾？

## 一亿多 token 主要花在反复带着历史继续工作

Token 是 AI 计算文字用量的单位。这个数字包含输入和输出，也包含多次读入相同历史的计量。

最初，让 Codex 从头监督到尾很有帮助。流程还没成熟，出了问题，它能查原因、改工具，再继续生产。但一个问题接着一个问题，同一次对话就越来越长。

那次制作记录了 16 次失败流程，其中 12 次发生在中文翻译和圣经引用核验环节。每次都需要查看错误、补充解释、调整、重跑、再检查。这里说的是流程失败，不能直接当作 16 次 AI 请求失败。

返工增加的不只是修改那一句话的工作。为了继续处理，AI 后续还会再次读入此前的要求、结果和排查记录；这些历史随着制作过程继续增长。我们又把海报和部分工具改造接在同一个会话里，主任务之外也有三个子任务继续工作。

像一场越开越长的工作会议：新的问题还没讲，就先带上之前所有的会议记录。

**出错和返工，让对话轮次变多；长历史在更多轮次中重复输入，让累计 token 继续膨胀。** 这是我们复盘后重点要改的地方。

## 为什么缓存率很高 仍然值得改流程

那次 Codex 输入中，98.73% 命中了缓存。用普通语言说，就是很多输入内容以前已经读过，可以复用已有的部分。

高缓存率在这里与大量重复历史相伴：同一段要求、同一份结果、同一个故障的上下文，在后续排查和返工中再次出现。缓存缓解了重复输入的负担，却没有替我们消除反复检查、等待和修改。

所以我们开始同时看两个问题：哪些旧内容能复用，以及为什么还需要这么多轮工作。仅仅把缓存率提高，无法回答后一个问题。

这 1.69 亿不能直接理解成账单，也不能全部算成翻译成本。它包括缓存输入、监督制作、海报及部分工程工作；真正用于文本生产的另一组 API 记录约为 172 万 token。两者各有计量范围。我们能确认返工会放大监督工作，但还没有逐次量出每个错误贡献了多少 token。

## 换了监督方式 为什么制作还是慢

后来，我们用 Agents API 搭了一个专门的后台监督流程，接手部分工作。流程更容易记录停在哪一步，发生中断后也更容易按原有记录继续。

这个迭代有价值，但内容生产仍然要经过翻译、复核、配音和试听。翻译有问题需要修；发音不对需要重做；一句中文变长，还要重新检查后面的播放节奏。换一种监督方式，并不会让这些工作自动消失。

我们也遇到过更直接的教训：页面文件检查和预览试听完成后，实际播放仍出现英文覆盖不完整、节奏不匹配。赶在截止时间前把文件交出去，还不足以证明会众能顺畅跟上。

因此，后续生产要求先核清英文内容，再做翻译；不能为了配合播放时间而删掉意思。省时间需要减少可避免的返工，同时保留必要的内容审核和试听。

## 我们已经做了什么 还在改什么

**先减少重复做同一件事。** 那次发音修订，我们重新生成了 8 个音频单元，保留并验证复用了另外 118 个。翻译也已有按小组保存结果和修复的能力。一个地方有问题，就尽量保留其他已经做对的部分，而不是因为局部错误把整篇再做一遍。修过声音之后，仍要检查整篇的衔接。

**再把每次出错都要讨论的事情固定下来。** 哪一步已经完成、下一步是什么、哪些结果还能用，正在改为由程序保存和检查。方案是让 AI 只收到当前需要判断的小问题，不默认带着整晚的对话继续处理。工具本身出了新问题，再交给 Codex 做工程修复。

**同时安排可以独立进行的工作。** 不同语言不必事事互相等待，但可能共用同一台配音设备。我们正在验证怎样把这些工作排好，既减少空等，又避免大家一起抢资源。已有本地模拟验证了部分安排和恢复方式，真实完整制作能快多少还要继续测。

**把生产和改造工具分开。** 本周内容交付有明确终点。海报、工具升级和新实验各自安排，避免一份生产任务无限延长，也让我们能看清真正制作内容用了多少时间。

## 下一轮 我们重点盯三段时间

第一段是**翻译和审核**。多语言会增加工作量，引用、术语和意思的遗漏又容易触发修订。我们希望错误尽早被发现，修完后只重查受影响的内容。

第二段是**配音和同步**。声音生成需要设备时间，修一句还可能影响前后衔接。已有音频复用解决了一部分重复生成，接下来还要看重新安排节奏和整篇试听花了多久。

第三段是**人工确认和等待**。译文、发音和播放效果仍需要人判断。材料何时准备好、问题是否集中呈现、改动是否清楚，会影响人能不能及时完成审核。

这三段是我们接下来重点测量和改进的地方，尚不是已经量出的瓶颈排名。我们会分别记录正常制作、失败返工和等待时间，比较同样内容、同样质量要求下的完整交付。

这一轮最有用的认识是：每解决一个错误，都应该让下周少一次同样的排查。减少反复读历史、重复生成和等待，才有机会把有限的一晚更多地留给内容质量与实际试听。
