# 在 10 到 12 小时内完成证道内容生产的挑战与方案

我们在做一个帮助中文会众跟上英文证道的个人项目，后来也把生产流程扩展到韩语和西班牙语。从拿到源视频，到下一场证道开始，通常只有约 10–12 小时。我们需要在这个窗口里完成转写、翻译、审核、配音、同步和页面交付，还要留出实际试听与故障恢复的时间。

最早，我们让 Codex 监督整个流程。它能读代码、运行工具、分析错误，也能当场补齐缺失的能力，帮助我们把流程做出来。但随着生产链变长，我们遇到了两个明显的痛点：完成一次制作需要很长时间，监督过程也消耗了大量 token。

随后，我们把一部分控制流程迁到 Agents API。工具权限更明确，会话可以持久化，恢复也更有章法，但耗时长的问题仍然存在。回头看，迁移改进了控制循环的运行方式，生产链上的依赖、等待和返工仍需要另外解决。

这篇文章整理我们踩过的坑，以及正在推进的方案：用确定性程序推进已知流程，用有界 Agent 处理少量不确定问题，让 Codex 负责工程开发和未知故障。部分组件和本地集成已经验证，真实完整生产的提速收益还需要测量。

本文依据截至 2026 年 10 月 1 日的仓库代码与记录整理。项目与 Mariners Church 无隶属关系。

## 交付窗口里到底要完成什么

输入虽然是一个视频链接，交付物却包含一整条相互依赖的链。

首先，我们要确认拿到的是正确版本的完整视频，保存来源、时长和文件哈希，并由人工确认证道开始与结束的位置。接下来，英文转写要绑定原声时间轴，听不清或未对齐的内容要显式保留，不能默默跳过。只有英文来源稳定，后面的翻译和音频才有可靠的输入。

我们把预制生产分成四个业务层：

1. **英文来源与锚点。** 冻结来源、证道范围、英文内容及原声时间轴。
2. **目标语言文字。** 按组翻译，进行独立模型复核、语言专项检查和人工文字审核。
3. **目标语言音频与同步。** 从同一版本文字合成音频，排程、装配、验证并完成听审。
4. **多语言交付与播放。** 构建匹配的发布包，发布页面，核验远端文件与播放器行为。

这些依赖会直接影响时间安排。英文来源改动，所有语言的下游都可能失效；某一种语言的文字修订，只应影响这一种语言。页面 HTTP 核验通过，也只说明相应远端交付检查通过，设备播放和现场同步还需要各自验证。业务包与失效规则见[四层接口合同](../multilingual-production-interfaces.zh.md)。

10–12 小时是从视频可用到使用时刻的日历窗口，包含人工等待、资源排队、失败恢复和试听。即使模型计算能在几小时内结束，只要人审或恢复卡住，我们仍然可能赶不上。

## 用 Codex 监督整条链时遇到的两个问题

Codex 对早期系统很有帮助。我们的流程尚未稳定，有时缺一个脚本，有时碰到未知错误，有时需要临时修改验证器。在这样的阶段，让一个能理解代码和业务的 Agent 把工作串起来，能推动很多原本走不通的步骤。

随着固定流程逐渐形成，监督会话却仍然承担了大量日常工作：读取状态、判断下一步、调用工具、等待结果、再次检查，再决定是否继续。相同的来源信息、审核要求、工具输出和故障历史不断进入后续轮次。一个会话还可能从制作内容一路延伸到海报、代码改造和文档更新。

这既拉长了监督过程，也让上下文越来越大。

### 历史记录里的时间和 token

2026 年 9 月 20 日的一次制作，处理的是约 32 分钟的证道。从收到制作指令到最终已审核页面完成 HTTP 核验，日历跨度为 **5 小时 46 分 54 秒**。这段时间包含人工等待、对话、排错和并行工作，不能全部归因于 Codex 或模型计算。

同一份记录中，文本生产 API 按唯一响应去重后累计 **1,716,038 token**；Codex 主任务和三个明确子任务的会话小计为 **169,298,693 token**。Codex 输入中 **98.73% 是缓存读取**，非缓存输入为 **2,148,134 token**。

这组数据需要连同口径一起读。1.69 亿主要反映长会话历史在多轮输入中的重复计量，不是证道内容的长度，也不表示全部按非缓存价格收费。这个会话范围还包含海报和部分流程工程工作，不能把全部用量都算成建立页面的必要成本。Codex 会话与生产 API 来自不同计量来源，也不能直接拼成一张账单。[历史制作记录](../production-2026-09-20.zh.md)和[token 分析](../reports/20260929-codex-orchestration-token-analysis.zh.md)保留了具体边界。

这里暴露出一个架构问题：生产状态长期留在会话历史里，正常运行与工程开发也缺少清晰的终点。缓存能改变重复输入的计费和处理方式，但仍需要控制会话承载的范围。

### 耗时不能只看某一次模型调用

那次制作还记录了 16 次失败流程，其中 12 次来自和合本翻译及引用核验。这是流程运行次数，不等于 API 请求失败次数。我们花时间处理的内容包括引用位置、英文覆盖、发音、时长预算和同步装配。

这些工作说明，端到端耗时受到多种因素影响。调度 Agent 的响应延迟、翻译和复核计算、音频合成、人工等待、返工次数，都需要分别记录。把调度模型换快一点，未必能改变当天最晚完成的那条生产路径。

## 迁到 Agents API 后的优点与代价

我们接入的 Agents API Supervisor 使用受限工具，本地脚本继续负责实际下载、生成和验证。服务端保存会话，本地保存工具请求、结果及阶段证据，恢复时尽量继续原会话。它当时的主要生产范围是双 PDF；不能把这个 Supervisor 的完成状态理解成四层多语言交付完成。具体边界见[Supervisor 合同](../sermon-production-supervisor-agent.zh.md)。

从我们的使用方式看，这次迁移有以下取舍：

| 方面 | 优点 | 代价和限制 |
|---|---|---|
| 工具权限 | Agent 只调用明确暴露的工具，本地工具再次检查门禁 | 需要维护工具合同、状态绑定和恢复规则 |
| 会话恢复 | 可以继续原 session，复用已经保存的工具结果 | 超时、断线和结果未知仍需核对，不能直接另开会话重跑 |
| 工程边界 | 生产控制更容易与通用代码开发分开 | 原有业务脚本的缺陷和耗时不会因此消失 |
| 运行时间 | 控制循环更便于测试和计量 | 翻译、复核、TTS、人审及返工的依赖仍然存在 |

所以，我们保留了 Agents API 的价值，同时重新审视它应该介入的位置。对于“哈希是否一致”“批准是否齐全”“这个固定阶段之后运行什么”这类已经有规则的问题，继续让模型逐步判断，会增加本可由程序完成的工作。

我们也试过比较不同调度模型。但已有小样本不能证明稳定的端到端速度优势。更低的单次费用、更短的一次响应，只有放回同输入、同质量门槛、包含失败恢复的完整流程里，才知道是否改善交付。[效率研究记录](../reports/20260929-weekly-workflow-efficiency-findings.zh.md)保留了这些实验限制。

## 内容质量和返工给我们的教训

时间压力很容易让团队把“流程跑完”当作“交付完成”。我们确实踩过这个坑。

9 月 20 日的页面文件核验和预览试听完成后，当日实际播放仍暴露出英文覆盖不完整、中英文节奏不匹配的问题。现场反馈没有逐段录音与遥测支持，我们不能据此确定每一处根因；但它明确说明，先前的通过证据没有覆盖真实播放的全部质量要求。

因此，后续生产要求先冻结英文、完成原声对齐和缺口审核，再进入翻译。中文需要完整覆盖原意，不能为了塞进时间槽而删掉内容；音频还要保持自然语速。机器筛查、文件可播放和哈希匹配，都不能代替这些质量检查。

另一条教训是控制返工范围。改一个发音，不应该重新合成整篇音轨；改一个语言，不应该重新翻译其他语言。那次发音修订已有实际复用记录：重新生成 8 个单元，验证复用另外 118 个。但音频单元复用后，仍可能需要重新排程、装配和听审。某句话变长，会影响后面的同步关系。

还有一种特别麻烦的失败：客户端超时了，服务端可能已经生成并收费。没有拿到结果，不能直接解释成没有执行。我们需要保存请求身份和原始响应，先核对结果；已返回的内容尽量本地恢复，无法确认的尝试保留为未知。盲目重跑会同时增加时间、费用和状态混乱。

因此，我们设计恢复时遵守两条边界：保留旧候选和审核证据，在新修订中修复；依据真实输入变化确定失效范围，复用仍有效的翻译与音频。源文件、文字、声音参数或策略变了，都需要重新核验相应的依赖。

## 我们设计的三层控制方案

四层业务生产描述的是产物之间的依赖。我们另外设计了三层控制职责，决定由谁来推进这些工作。

### 确定性工作流引擎推进正常路径

固定程序读取持久化状态，核验来源身份、文件哈希、收据、审批和预算，然后运行合法的下一阶段。每个阶段要能检查、执行、验证和恢复；同一份输入重复调度，不能产生重复付费或重复发布。

运行状态保存在文件、账本和 durable job 中。重启后，程序能知道哪个任务仍在运行，哪个结果已经保存，哪个审核仍在等待。等待人审时，系统保存状态并返回；收到绑定当前版本的真实批准后，再继续推进。

正常路径的设计目标是 **runtime Codex 编排轮次为 0**。翻译和内容复核仍然可以调用模型，人审也继续保留；这个目标只是把固定状态转换从 Codex 会话中移到程序里。当前局部适配器和组件验证不能证明完整生产链已经达到这个目标。

### 有界 Decision Agent 处理真正存在歧义的问题

如果程序遇到尚不能分类的失败，或存在多个合法恢复路径，才提交一个窄问题给 Agent。

它收到的是小型状态包：当前阶段、受影响单元、版本、短错误码、允许动作及证据引用。完整证道、长日志和父任务历史不默认进入输入。Agent 的输出是结构化建议，程序重新读取当前状态，验证建议是否仍合法，再按原来的执行和审批合同处理。

我们还限制它的调用次数、时间、预算与读取范围。同一个疑点不能靠无限增加上下文反复尝试。另一个只读诊断通道可以帮助定位缺失证据或提出原因假设，但诊断建议本身不具有修改、重试、批准或发布权限。

### Codex 处理工程开发与未知故障

当现有规则无法恢复，或发现脚本、schema、验证器本身存在缺陷时，再进入工程任务。Codex 负责分析根因、修改代码、补充相关验证并提交变更。

修复完成后，能够固定下来的判断沉到工作流引擎里；仍需要模型判断的窄问题形成有界合同。随着已知问题增多，正常生产就能少依赖长时间驻留的工程会话。

页面交付也有明确终点。海报、流程改造和新实验按各自授权范围开展、单独记账，避免继续扩大本次生产会话。[三层重构设计](../codex-orchestration-pipeline-design.zh.md)记录了身份、预算、恢复和阶段验证要求。

## 针对耗时的设计还需要依赖图和资源调度

减少监督 token 只是其中一部分。要缩短从视频到交付的时间，还需要找出最晚完成的依赖链，并减少这条链上的等待和重复工作。

我们把共享英文来源后的语言分支画成依赖图，也就是 DAG。英文来源通过后，中文、韩语和西班牙语在业务上可以独立推进；某语言的翻译组也可以在策略允许的范围内并发。所有分支仍须完成本语言的审核、音频包和发布门禁。

业务独立不代表资源无限。不同语言可能共用 API 配额、同一块 GPU 或同一个本地模型。提高任务并发数，可能只把等待移到资源队列。调度需要同时核对资源容量、预算和任务身份；共享状态的修改还需要锁和 lease。

我们的发布计划也保留明确的汇合要求。如果本轮要求等三语音频都完成再发布，就等三语完成。语言独立生产能够缩小故障影响，但不能绕过这个发布决定。

Prefect 是这一阶段的本地编排试点，用来验证任务依赖、受限资源池、失败隔离和恢复。它复用原有业务证据与门禁。框架显示任务 Completed，仍然需要原始产物、审核和批准收据才能判断业务完成。

进度与预计完成时间也遵守同样的原则。处理过多少工作、机器审核通过多少、人工批准多少，分开显示。预计完成时间需要同类真实样本、当前队列和运行状态；缺少资源信息、结果未知或正在等待人审时，允许显示未知。我们希望操作人员能据此安排时间，而不是得到一个依据不足的倒计时。实现口径见[进度与 ETA 文档](../offline-run-progress-eta.md)。

## 已经验证的部分和下一步要证明的事

现在，我们已有逐组模型响应缓存、部分翻译修复、按音频单元复用，以及固定 Layer 2 执行适配器。后者可以接入既有文字 producer，但停在人工文字审核门槛，尚不能代表完整四层自动生产。[Layer 2 适配器说明](../canonical-layer2-controller.zh.md)列出了具体范围。

截至本文核查时，本地 Prefect 引擎已经跑过一个 10 节点的 mock 集成，覆盖共享来源和三语文字、音频、页面分支。完成路径重放时复用了相同任务、输出、收据和预算预约；一个语言的已知失败只阻塞它的后继；结果未知则保留占用和阻塞，没有自动重试。

这验证了部分调度与恢复机制。业务回调仍是确定性的 mock，人工观察也是明确标记的模拟证据，没有真实人工批准。生产业务适配器、真实资源监测和 live Agents 诊断连接尚未在这个集成里接通。因此，**本地 mock 集成通过，仍不能证明真实三语生产已经提速**。[集成报告](../reports/20261001-prefect-pilot/README.md)保留了这些结果和缺口。

接下来，我们按固定夹具、真实小片段、10 分钟片段、完整往期视频的顺序验证，并加入故障恢复演练。固定回放检验合同和恢复；真实片段测量模型与音频性能；整篇运行检验规模扩大后是否仍然成立。

我们优先要求以下行为能被证据证明：

- 未受影响的成功翻译组，恢复时新增付费调用为 0。
- 已验证、输入未变的音频单元，恢复时重新合成为 0。
- 上传或 HTTP 核验失败后，恢复不重跑 ASR、翻译和 TTS。
- 日历总耗时、资源排队、人工等待、返工和各类 token 用量分别可追溯。
- 在同一来源、同一质量门槛下比较，并保留失败、废弃修订和未知用量。

这些指标通过后，我们才有依据讨论节省了多少时间与 token，以及能否稳定落在 10–12 小时的交付窗口内。

我们仍然需要 Agent 的理解和判断能力，也需要 Codex 持续改进系统。现在的设计把这些能力放在明确的位置：固定程序承担日常推进，Agent 处理受限的歧义，Codex 解决工程问题。对每周只有一晚生产窗口的项目来说，我们希望每次遇到并解决的问题，都能变成下一次运行时可复用的规则。
